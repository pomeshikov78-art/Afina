# Регламенты миграции, резервного копирования, восстановления и обновления (позиция 13, §11.1)

## 1. Резервное копирование
- Инструмент: `src/tools/backup.py` (снимок sqlite backup API — консисентен под нагрузкой; манифест sha256 на каждый файл; опционально каталоги data/ и archives/).
- Периодичность (RPO): по умолчанию 1 ч (rpo_policy_s=3600 в манифесте); перед каждым утверждением базовой линии — внеочередной снимок.
- Хранение: `backups/` внутри контура; вынос — только контролируемым переносом (п. 4).

## 2. Восстановление (RTO)
- `backup.py verify` → `restore` → `integrity_check` (аудит-цепочка + счётчики реестров). Замер полного цикла: `backup.py drill` (факт в песочнице: доли секунды на БД ≤ 10 МБ; на стенде фиксируется актом).
- После восстановления: повторный прогон `pmi/run_132.py` (шаги 1–10) или смоука — подтверждение целостности связей.

## 3. Миграция (§4.13.4, DAT-005)
Инвентаризация источников → пробный перенос на репрезентативной выборке → контроль полноты/качества (validate_object) → протоколирование → повтор без повреждения исходного архива. Контроль целостности при переносе — migration_hash_check (dat.py). Исходные файлы и происхождение остаются неизменными.

## 4. Контролируемый перенос (AUT-T05/T07)
Переносимый комплект = манифест + файлы с sha256 (тайлы — tiles_rsc манифест; БД — backup манифест; бандл — bundle_manifest.json). На приёме: verify → при несовпадении хэша комплект ОТКЛОНЯЕТСЯ до восстановления, событие пишется в аудит (класс sec).

## 5. Обновление и откат
1. Снимок текущего состояния (п. 1) ДО обновления.
2. Установка пакета (Windows: NSIS/Inno; Linux: build_linux.sh → каталог+ярлык; проверка целостности run_server.pyw при старте).
3. Прогон регрессионного набора (Руководство сопровождения §4); при неуспехе — откат: восстановление снимка + предыдущая версия кода (git-тег релизной линии).
4. Обновление не переписывает утверждённые результаты задним числом (CFG-004): прежние расчёты сохраняются со своей конфигурацией и версией модели.
