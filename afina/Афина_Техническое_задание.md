# 1. ОБЩИЕ СВЕДЕНИЯ

## 1.1. Назначение системы

СПО «Афина NextGen» (далее — Система) предназначено для создания, анализа, оптимизации, верификации и сопровождения цифровых моделей территорий, телекоммуникационных сетей, радиоэлектронного оборудования, инженерных сооружений и организационной структуры подразделений связи на всех стадиях жизненного цикла:

**требование → техническое решение → модель → расчёт → документация → изделие → испытания → эксплуатация → модернизация.**

Система объединяет в едином рабочем пространстве:

- геоинформационное ядро и трёхмерную интерактивную среду;
- инженерные расчёты распространения радиоволн, энергетики, теплового режима, сетевой связности и надёжности;
- инженерный каталог средств, библиотек моделей и цифровых двойников;
- учёт подразделений связи, организационно-штатной структуры и фактического технического состояния;
- сценарное моделирование воздействий, устойчивости и восстановления;
- управление требованиями, конфигурацией, изменениями и доказательствами соответствия;
- локальные ИИ-сервисы, обучение и геймифицированное проектирование;
- автономную эксплуатацию в защищённом контуре и полностью изолированном комплексе.

## 1.2. Границы системы и ограничения применения

**1.2.1.** Система является инструментом **инженерной оценки и доказательного проектирования**. Она не заменяет:

- специализированные прочностные расчёты конструкций;
- полигонные и приёмочные испытания изделий;
- уполномоченные нормативные и санитарные проверки;
- решения комиссии, заказчика и ответственных специалистов.

**1.2.2.** Военный профиль ограничен задачами проектирования, оценки устойчивости, защитного исполнения, сохраняемости функций и восстановления инфраструктуры.

**В Системе не реализуются:** расчёт эффективных способов поражения, выбор прицельных параметров и уязвимых точек, оптимизация применения оружия, планирование маршрутов проникновения и обхода охраны, автоматический выбор позиций и режимов действий против средств разведки. Воздействия задаются как **нормализованные инженерные профили последствий**.

**1.2.3.** ГИС «Оператор» / «Оператор SE» рассматривается **только как функциональный референс и источник требований к форматам обмена**. Система не разрабатывается как надстройка над «Оператором» и не содержит его исходного кода.

**Запрещается** реверс-инжиниринг закрытых компонентов. Использование форматов, библиотек и API допускается исключительно при наличии подтверждённых правообладателем лицензий и документированных интерфейсов. Фактическая доступность этих интерфейсов подтверждается на этапе G0.

**1.2.4.** ENG6+ — проектное обозначение вычислительного ядра Системы. Его состав, API и характеристики подтверждаются на этапе G0–G1 и фиксируются в реестре моделей.

## 1.3. Термины и сокращения

| Термин | Определение |
|---|---|
| Цифровой двойник (ЦД) | Управляемая совокупность геометрии, конфигурации, моделей, наблюдений и истории объекта; не обязательно работает в реальном времени |
| КСИМ-ДД | Каталог средств, инженерных моделей и цифровых двойников |
| ENG6+ | Вычислительное ядро инженерных расчётов Системы |
| Digital Thread | Сквозная прослеживаемость «требование — решение — модель — расчёт — документ — испытание — эксплуатация» |
| ОШС | **Организационно-штатная структура**. В данной редакции термин используется только в этом значении |
| V&V | Верификация (корректность реализации) и валидация (соответствие реальности) |
| Базовая линия | Утверждённая, неизменяемая конфигурация проекта |
| Паспорт расчёта | Машиночитаемое описание запуска: данные, модели, среда, параметры, допущения, результат |
| LOD / LOD-генерализация | Уровень детализации геометрии и отображения |
| ПМИ | Программа и методика испытаний |
| RTM | Матрица прослеживаемости требований |
| Air-Gap | Полностью изолированный комплекс без физических внешних сетевых подключений |
| SBOM | Реестр сторонних программных компонентов и лицензий |

**Устранение терминологического конфликта:** индикатор статус-бара, ранее обозначавшийся «ОШС и ресурсы», в настоящей редакции именуется **«Ошибки и ресурсы»**. Термин «ОШС» резервируется исключительно за организационно-штатной структурой подразделения.

## 1.4. Приоритеты требований

| Приоритет | Значение | Правило приёмки |
|---|---|---|
| **P0** | Критический | Без выполнения требование блокирует соответствующий этап приёмки |
| **P1** | Обязательный | Входит в утверждённый объём поставки; перенос возможен только решением Заказчика |
| **P2** | Значимый | Реализуется в очередном этапе развития при согласованном составе |
| **P3** | Перспективный | Не является основанием для приёмочных претензий |

> Статус P1 **не означает** автоматического разрешения перенести функцию за пределы контракта.

## 1.5. Разделение статусных моделей

Система обязана хранить следующие статусы **раздельно**, не подменяя один другим:

| Модель | Значения |
|---|---|
| Качество данных (DAT) | Не заполнено → Введено → Формально проверено → Подтверждено источником → Подтверждено измерением; отдельно: Устарело, Конфликт, Отозвано |
| Техническое состояние (TS) | TS-0…TS-8 (разд. 4.4) |
| Жизненный цикл ЦД | DESIGN, APPROVED, AS_BUILT, OBSERVED, DIAGNOSED, PREDICTED, RESTORED — нелинейный граф |
| Зрелость модели | DRAFT → UNDER_REVIEW → VALIDATED → RESTRICTED → DEPRECATED |
| Изменение | Предложено → Внесено → Проверено → Утверждено |
| Уведомление | Создано → В очереди → Доставлено → Просмотрено → Подтверждено → Исполнено → Закрыто |
| Требование | Проект → Утверждено → Реализуется → Проверяется → Принято / Отклонено |

# 2. ЦЕЛИ И ИЗМЕРИМЫЕ РЕЗУЛЬТАТЫ

| Цель | Измеримый результат |
|---|---|
| Сокращение цикла «данные → проверенный проект» | Сокращение числа ручных операций и времени типового расчёта относительно базового процесса Заказчика |
| Снижение CAPEX | 15–20 % за счёт виртуального подбора мест размещения и сравнения альтернатив |
| Снижение OPEX | За счёт предиктивного обслуживания и оптимизации энергопотребления |
| Доказательность | 100 % опубликованных инженерных результатов имеют паспорт расчёта |
| Прослеживаемость | 100 % обязательных требований связаны с реализацией, тестом и протоколом |
| Воспроизводимость | 100 % эталонных расчётов воспроизводятся в установленных допусках |
| Автономность | 100 % заявленных функций выполняются без внешних сетевых обращений |
| Сохранность | RPO = 0 для зафиксированных транзакций; RTO ≤ 15 мин (проектная цель, уточняется на G1) |
| Качество данных | ≥ 98 % заполненности обязательных применимых атрибутов; 0 необъяснимых потерь при round-trip |

Численные пороги, зависящие от аппаратуры и объёмов данных, утверждаются актом по результатам этапа G1 и фиксируются в Приложении З.

## 3.4. Два режима эксплуатации (единое ядро)

### Режим А — автономный защищённый контур
- Интернет отсутствует; внутренняя ЛВС разрешена.
- Многопользовательская работа, локальные серверы, СУБД, GPU-кластер.
- Внутренние API, телеметрия, интеграции с EAM/ERP.
- Централизованные администрирование, резервирование, аудит.

### Режим Б — полностью изолированный комплекс (Air-Gap)
- Физическое отсутствие внешних сетевых подключений.
- Автономное рабочее место **или** замкнутая локальная сеть.
- Все ГИС-данные, модели, ИИ-весы, справочники — локально.
- Обмен — только через разрешённые носители и утверждённую процедуру.
- «Push» означает **внутреннюю** доставку уведомления, а не интернет-канал.

### Обязательные архитектурные требования

| ID | Требование |
|---|---|
| AUT-001 | Оба режима реализуются на **едином программном ядре**, с общими форматами проектов и моделями |
| AUT-002 | Ни один критический сценарий не требует Интернета, облачной авторизации или удалённого API |
| AUT-003 | Режим фиксируется при развёртывании и защищён от несанкционированного изменения |
| AUT-004 | Обеспечен контролируемый экспорт/импорт проектов, ЦД, результатов и библиотек с проверкой версий, целостности и зависимостей |
| AUT-005 | Перенос данных **не создаёт автоматического сетевого моста** между контурами |
| AUT-006 | Работоспособность каждого режима подтверждается **отдельным протоколом испытаний** |
| AUT-007 | При физическом отключении внешних интерфейсов выполняется полный согласованный набор сценариев |
| AUT-008 | Сетевой мониторинг при установке, запуске, расчёте, ИИ-запросе, обновлении и отчётности не выявляет неразрешённых исходящих соединений |

## 3.5. Роли и разделение полномочий

| Роль | Полномочия | Ограничения |
|---|---|---|
| Проектировщик | Создание и редактирование моделей | Не утверждает базовую линию |
| Инженер-расчётчик | Запуск расчётов, интерпретация, паспорта | Не утверждает чужие результаты без процедуры |
| Инженер-верификатор | Проверка моделей, данных, воспроизводимости | Не изменяет утверждённые данные напрямую |
| ГИС-аналитик | Импорт, качество геоданных, слои | Доступ в рамках категории данных |
| Администратор данных | Справочники, классификаторы, миграции | Не утверждает инженерные решения |
| Руководитель программы | Панели, контроль этапов, назначение | Не подменяет экспертное утверждение |
| Уполномоченный утверждающий | Базовые линии, допуск результатов | Действует в рамках регламента |
| Аудитор | Чтение журналов, доказательной базы | Без права изменения |
| Администратор системы | Развёртывание, лицензии, резервирование | Действия логируются; не является автоматическим владельцем всех данных |

**Принцип Maker–Checker:** подготовка, проверка и утверждение критического решения принадлежат разным субъектам.

## 3.6. Основные сценарии использования

| Сценарий | Последовательность |
|---|---|
| A. Пространственное проектирование | Загрузка территории → размещение → предварительная оценка → точный расчёт → проверка ограничений → сохранение варианта |
| B. Радиопланирование | Выбор оборудования и частот → расчёт распространения → покрытие и интерференция → сравнение → отчёт |
| C. Эксплуатационный ЦД | Телеметрия → контроль качества → обновление состояния → обнаружение отклонения → оценка влияния → событие |
| D. Сетевая инфраструктура | Узлы → топология → трассы → потери и ресурсы → резервирование → стоимость |
| E. Сценарий устойчивости | Исходное состояние → воздействие → отказ/деградация → потеря услуг → восстановление → остаточная функциональность |
| F. Инженерный полигон | Требования → данные → архитектура → сборка → расчёт → сценарии → сравнение → защита проекта |
| G. Жизненный цикл изделия | ТЗ → проект → производство → монтаж → испытания → эксплуатация → модернизация |

# 4. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

## 4.1. Геоинформационное ядро (GIS)

### 4.1.1. Поддерживаемые данные

| Класс | Форматы | Требования |
|---|---|---|
| Векторные карты | SXF (ред. 4.0), MAP, SIT, SITX | До 256 слоёв; приоритеты отображения 0–255; сохранение семантики; SITX — шифрование 256 бит при наличии подтверждённого механизма |
| Растровые данные | RSW, GeoTIFF, BMP, JPEG | Тайловая структура, сжатие, метаданные точности и даты |
| Матрицы высот | MTW | Построение по горизонталям, отметкам, 3D-метрике; формирование экстремумов; средневзвешенная интерполяция |
| Матрицы качеств | MTQ | Тепловые карты покрытия, настраиваемая палитра, численная легенда |
| Матрицы слоёв | MTL | Геологические и тематические слои |
| TIN | TIN-модели | Нерегулярная триангуляция рельефа |
| Облака точек | MTD, LAS/LAZ | Лазерное сканирование, классификация поверхностей |
| 3D-тайлы | DB3D | Pyramids GoogleMapsCompatible (EPSG:3857), GoogleCrs84Quad (EPSG:4326); уровни 10–22; поддержка до 20–30 Гбайт на тайл-пакет уровня 12 |
| BIM / 3D | IFC, CityGML (LOD1–LOD3), glTF/GLB, OBJ, STEP | Сохранение семантики, материалов, монтажных зон |
| Классификаторы | RSC | Условные знаки, семантические коды, локальные расширения |
| Обменные | GeoJSON, GeoPackage, Shapefile, KML, GML, DXF, MIF | С фиксацией потерь при преобразовании |

**GIS-001.** Для каждого набора данных хранятся: система координат, высотная система, точность, масштаб/разрешение, дата съёмки, источник, допустимая область использования.

**GIS-002.** Преобразование координат выполняет фактический пересчёт с записью применённой операции и параметров. **Запрещено** менять только подпись CRS без пересчёта геометрии.

**GIS-003.** Поддержка СК-42, СК-95, WGS84, UTM, МСК и локальных систем; встроенный реестр проекций; библиотека трансформаций с версионированием.

**GIS-004.** Round-trip импорт → экспорт → импорт не влечёт необъяснимой потери атрибутов, связей, координат и семантики. Потери фиксируются в протоколе.

### 4.1.2. Редактор оперативной обстановки

Система должна обеспечивать:

- создание объектов из классификатора и по коду существующего;
- нанесение условных знаков **по сценарию** и комбинированным методом;
- работу с участками объектов, наборами объектов, составными подписями;
- перемещение, удаление, изменение цвета, масштаба, типа объекта;
- выравнивание выделенных объектов, зеркальные копии, разворот флагов;
- нанесение и редактирование совмещённого командного пункта (выноски);
- текстовые и криволинейные подписи, подписи линии по семантике;
- быстрое редактирование;
- массовое редактирование семантики списка объектов;
- настройку цветов и границ видимости;
- измерение расстояний с построением ортодромии, площадей, высот, уклонов;
- отмену и повтор любой операции;
- завершение операции несколькими эквивалентными способами (клавиатурная комбинация, двойное нажатие, сочетание кнопок мыши) — с единой семантикой результата.

### 4.1.3. Сценарное нанесение

Система поддерживает сценарии нанесения в текстовом формате (`.OSC`) со следующим набором команд:

| Команда | Назначение |
|---|---|
| `OBJECTSSCRIPT` | Начало файла |
| `.GROUP` / `.SCENE` | Группа / сценарий |
| `INIT <код>` | Создание объекта по ключу классификатора |
| `SUBJECT` | Создание подобъекта |
| `COMMIT` | Сохранение объекта |
| `QUIT` | Завершение режима создания |
| `STAFF`, `STAFFON`, `STAFFOFF` | Формирование комбинированного КП / выноски |
| `POINT1`, `POINT2`, `REMEMBERPOINT N <текст>` | Опорные точки и мнемоники |
| `SPLINEON`, `ANYPOINT`, `ARBITRON` | Режимы графического ввода |
| `SEM <код> <значение>` | Присвоение семантики |
| `TEXT <значение>` | Создание подписи |

Поддержка метрик: `XY`, `H` (3D), `R` (развёрнутая метрика), `GMS` (градусы/минуты/секунды), `QUADRO`.

**Требования:**
- синтаксическая проверка сцены с указанием ошибочной строки;
- выполнение, пауза, остановка;
- хранение сценариев локально;
- поддержка сценариев анимации отображения (`scenario.xml`) с запуском, паузой, остановкой;
- служебные файлы параметров сеанса (INI) хранятся вместе с паспортом карты;
- сохранение видов карт и расположения панелей между сеансами.

### 4.1.4. Производственные ГИС-функции

- Создание матриц высот по векторным объектам с фильтром состава (`IMH`).
- Создание растра по картматериалам с фильтром объекта и цвета (`MAP2RSW.INI` — аналогичный механизм, реализованный средствами Системы).
- **Оптимизация матрицы** и **сжатие с оптимизацией**; опция создания резервной копии исходника.
- Построение произвольного участка карты и растра.
- Формирование экстремумов рельефа внутри замкнутых горизонталей.
- Границы видимости и зоны видимости (сектор с экрана или по параметрам).
- Профиль местности по матрице высот с учётом относительных высот сооружений.
- Буферные зоны, пересечения, кратчайшие пути по графу дорог.
- Печать карты и отчёта с калибровкой, цветоделением и векторным/растровым выводом.

## 4.2. Трёхмерная среда и интерактивное проектирование (3DM)

**3DM-001.** Каждый объект сцены имеет устойчивый идентификатор, сохраняемый при редактировании, переименовании и перемещении.

**3DM-002.** Поддержка режимов: 2D, 3D, вертикальный срез (Z-срез этажей), сравнение двух сценариев.

**3DM-003.** Интерактивное размещение «перетащи и поставь»:
- перетаскивание из каталога активов в сцену;
- интеллектуальная привязка (Snap-to) к рельефу, крыше, фасаду, мачте, монтажной позиции;
- проверка габаритов и сервисных зон при размещении;
- цветовая индикация недопустимого размещения с объяснением причины.

**3DM-004.** Двухуровневый отклик:
1. **При перемещении** — облегчённая модель (Preview), предварительная тепловая карта, маркировка «предварительно».
2. **При отпускании (Drop)** — постановка точного расчёта в очередь; индикация «Выполняется точный расчёт…»; замена результата без изменения маркировки достоверности задним числом.

**3DM-005.** Автопрокладка линков при стыковке объектов: расчёт длины, затухания, стоимости, падения напряжения; сохранение основания выбранной трассы.

**3DM-006.** **Разделение детализации визуализации и расчёта.** Снижение LOD для повышения FPS не изменяет сохранённую геометрию, координаты и результаты расчётов.

**3DM-007.** Визуализация результатов:
- тепловые карты с численной легендой, единицами и диапазоном;
- границы применимости модели;
- неопределённость и диапазоны результатов;
- состояния «до / после воздействия / после восстановления»;
- граф зависимостей и затронутых услуг;
- временные графики и диаграммы;
- экспорт изображений с указанием версии модели.

**Запрещено:** визуально одинаково отображать отсутствие данных, нулевое значение и непроверенный результат.

**3DM-008.** Геометрические проверки: коллизии, сервисные зоны, доступность соединителей, радиусы изгиба кабельных трасс, монтажные ограничения.

## 4.3. Каталог средств, моделей и двойников (КСИМ-ДД / EQP)

### 4.3.1. Три разделённые сущности

1. **Тип изделия** — обобщённые свойства класса.
2. **Исполнение / экземпляр** — модификация, серийное изделие, фактически установленное средство.
3. **Расчётная модель** — представление для конкретного решателя.

> Наличие карточки изделия **не означает** наличия достоверной расчётной модели.

### 4.3.2. Классификатор

| Код | Группа |
|---|---|
| COM | Средства связи |
| ANT | Антенны и антенные системы |
| NET | Сетевое оборудование |
| SRV | Вычислительная инфраструктура |
| PWR | Электропитание |
| CAB | Кабельная инфраструктура |
| STR | Сооружения и размещение |
| SENS | Сенсорные и измерительные средства |
| NAV-TIME | Навигация и синхронизация |
| OBS | Средства наблюдения |
| EW | Средства радиоэлектронного воздействия и защиты |
| PHY-THREAT | Профили физических воздействий |
| PROTECT | Защитные средства |
| SW | Программное обеспечение |
| VEH | Транспортные и мобильные платформы |
| TOOL | Инструмент и испытательные средства |
| ENV | Внешняя среда |
| THREAT-PROFILE | Профили угроз и последствий |
| MODEL | Расчётные модели |

Классификатор поддерживает множественное наследование, локальные расширения без изменения ядра, синонимы, ссылки на нормативы с редакцией, даты действия, журнал изменений и обратную совместимость.

### 4.3.3. Карточка средства

Обязательные блоки:
1. Идентификация и происхождение (ObjectID, ClassID, обозначение, изготовитель, версия, VariantID, серийный номер, жизненный статус, источник, статус подтверждения, категория доступа, история).
2. Физико-конструкционные (габариты, масса, материалы, крепления, центр масс, сервисные зоны, вентиляция, условия монтажа и транспортировки).
3. Электрические (напряжение, род тока, мощности режимов, КПД, тепловыделение, заземление, разъёмы, АКБ, пусковые токи).
4. Радиотехнические (диапазоны, полосы, мощность **с указанием режима и точки измерения**, чувствительность **с методом определения**, ДН, поляризация, потери фидера, синхронизация, параметры ЭМС).
5. Сетевые и программные (протоколы и версии, интерфейсы, скорости, прошивки, зависимости, требования к ресурсам, защищённая загрузка).
6. Надёжность и обслуживание (ресурс, показатели **с условиями и методикой**, режимы отказов, регламенты, трудоёмкость, ЗИП, взаимозаменяемость, калибровка).

**EQP-001.** Система различает состояния значения: **«неизвестно»**, **«не применимо»**, **«не измерено»**, **«равно нулю»**. Подстановка условного значения вместо неизвестного запрещена.

**EQP-002.** Паспортные, измеренные, расчётные и экспертные значения хранятся **раздельно**, каждый со своим источником, датой и статусом.

### 4.3.4. Варианты и наследование

Поддержка: семейство → исполнение → конфигурация → параметрический экземпляр → проектная альтернатива → фактическая конфигурация.

- Наследование параметров с сохранением ссылки на источник.
- Переопределение создаёт новую версию, не уничтожая исходную.
- Изменение базового типа формирует список зависимых исполнений и проектов.
- Замена компонента запускает проверку совместимости и перечень пересчётов.
- Обновление каталога **не изменяет** ранее утверждённые проекты.

### 4.3.5. Движок совместимости (Compatibility Engine)

Проверки по 12 типам: геометрическая, электрическая, интерфейсная, протокольная, радиотехническая, электромагнитная, тепловая, конструкционная, программная, эксплуатационная, документальная, модельная.

**Результат — один из пяти статусов:**
`Совместимо` / `Совместимо с ограничениями` / `Несовместимо` / `Недостаточно данных` / `Требуется инженерное подтверждение`.

> **Отсутствие выявленного конфликта не равно доказанной совместимости.**

### 4.3.6. Мастер создания нового средства

Пошаговый интерфейс: выбор класса → идентификация → шаблон параметров → значения и единицы → документы и 3D → состав и варианты → интерфейсы → привязка модели → автоматическая валидация → экспертная проверка → публикация → уведомление зависимых проектов.

Уровень создаваемого объекта выбирается пользователем:
- только каталожная запись;
- каталог + геометрия;
- каталог + инженерные параметры и модель;
- полный цифровой двойник с жизненным циклом.

**Валидация при вводе:** обязательность полей, типы, размерности, диапазоны, противоречия, ссылки на источники, дубликаты, согласованность с базовым типом, корректность файлов, версия схемы, допустимость модели в выбранном режиме расчёта.

Ошибки классифицируются: **критические (блокируют публикацию) / предупреждение / информационное**.

### 4.3.7. Профили воздействий

Отдельный от каталога изделий реестр. Обязательные поля: `ThreatProfileID`, `ThreatClass`, `ScenarioType`, `TargetClass`, `InputParameters`, `TimeModel`, `SpatialModel`, `EffectModelID`, `ApplicabilityDomain`, `UncertaintyModel`, `ValidationEvidence`, `DataSource`, `AccessPolicy`, `Version`.

Профили описывают **инженерные последствия**, а не эксплуатационные характеристики средств поражения.

## 4.4. Подразделения связи, ОШС и техническое состояние (UNT)

### 4.4.1. Разделение штата и факта

Система ведёт одновременно:
- **ОШС** — утверждённая организационно-штатная структура с версией, датой действия и документом-основанием;
- **фактическую структуру** — реальное наличие подразделений, должностей и имущества;
- **агрегированные кадровые показатели** — укомплектованность по категориям и специальностям, квалификации и допуски.

Персональные данные хранятся только при наличии полномочий; аналитические представления используют агрегаты.

> Штатная должность не означает фактическое наличие сотрудника. Запись о наличии техники не означает её исправность.

### 4.4.2. Классификатор технического состояния

| Код | Состояние | Правило |
|---|---|---|
| TS-0 | Не оценено | Нет актуальных достаточных данных |
| TS-1 | Исправно | Подтверждено проверкой |
| TS-2 | Исправно с ограничениями | Допустимо только в зафиксированных пределах |
| TS-3 | Требуется обслуживание | Регламентная работа или некритичный дефект |
| TS-4 | Неисправно | Эксплуатация по назначению не подтверждена или запрещена |
| TS-5 | На ремонте | Выполняются ремонтные работы |
| TS-6 | На проверке | Уточняется по диагностике/испытаниям |
| TS-7 | Выведено из эксплуатации | Исключено из действующего фонда |
| TS-8 | Данные устарели | Истёк срок актуальности проверки |

Каждая фиксация состояния содержит: дату, основание, ответственное лицо, дефектную ведомость, ограничения, ссылку на документ или телеметрию.

> **«Не оценено» ≠ «неисправно». Отсутствие сведений ≠ исправность.**

### 4.4.3. Три уровня возможностей

| Уровень | Основание |
|---|---|
| **Заявленные** | Штатные документы, паспорта, требования |
| **Подтверждённые** | Испытания, акты технического контроля, документы |
| **Расчётные** | Моделирование в заданных условиях с допущениями |

Матрица возможностей охватывает: проводную, радиосвязь, радиорелейную, спутниковую связь; передачу данных; электропитание; техническое обслуживание; мониторинг; интеграцию.

### 4.4.4. Аналитика

Раздельно рассчитываются:
- организационная обеспеченность;
- техническое состояние (доли исправных, ограниченных, неоценённых; просроченное ТО);
- подтверждённость возможностей;
- качество данных.

**Методика агрегирования и правила исключения из знаменателя едины для всех подразделений одного типа.** Сводный балл не скрывает критических дефектов.

## 4.5. Инженерное ядро ENG6+ и математический аппарат (ENG / MOD)

### 4.5.1. Режимы расчёта

| Режим Системы | Режим ядра | Уровень модели | Назначение | Маркировка |
|---|---|---|---|---|
| **Preview** | `physics: fast` | L0 / часть L1 | Интерактив при перемещении | «Предварительный» |
| **Engineering** | `physics: auto` | L1–L2 | Проектные решения | «Инженерный расчёт» |
| **High Fidelity** | `physics: full` | L2–L3 | Спорные и сложные случаи | «Высокодетальный» |
| — | — | L4 | Верификационный контур | «Эталонная проверка» |

**▶ Расчёт (синхронно)** — локальные быстрые операции.
**⇶ Очередь (асинхронно)** — массовые и тяжёлые расчёты без блокировки интерфейса.

### 4.5.2. Уровни детализации

| Уровень | Назначение |
|---|---|
| L0 — концептуальный | Сравнение архитектур, порядок величин |
| L1 — инженерный | Проверка проектных решений, документированная область применимости |
| L2 — детальный | Узлы, материалы, специализированные решатели |
| L3 — имитационный | Поведение во времени, события, состояния |
| L4 — верификационный | Эталонные модели, измерения, контрольные эксперименты |

> Результат L0 **не может** автоматически считаться эквивалентом L2.

### 4.5.3. Математический аппарат

Система поддерживает (через собственные модули или документированные внешние решатели):

- алгебраические и балансовые уравнения, матричные и тензорные преобразования, **контроль размерностей**;
- обыкновенные дифференциальные уравнения и уравнения в частных производных;
- теорию графов: типизированные вершины и рёбра, потоки, зависимости, деревья отказов;
- численные методы: СЛАУ/нелинейные системы, интегрирование, интерполяция, краевые задачи, оптимизация, статистика;
- вероятностные модели: Марковские цепи, Монте-Карло, интервальная арифметика, байесовская оценка;
- дискретно-событийное, непрерывное и гибридное моделирование;
- многокритериальную и робастную оптимизацию.

**Физическая и логическая топологии хранятся раздельно.** Географическое соседство не создаёт технической связи автоматически.

### 4.5.5. Модели распространения и антенн

- Эмпирические: Окамура–Хата, COST-231, SUI, профильные рекомендации ITU-R.
- Полудетерминированные: SPM с калибровкой.
- Детерминированные: 3D Ray-Tracing / SBR, UTD-дифракция, рассеяние, проникновение через материалы.
- Полноволновые: FDTD, FEM — при наличии подтверждённой реализации.
- Специализированные: mmWave, indoor-outdoor, RIS, DAS.

Поддержка стандартов: GSM/UMTS/LTE/5G NR (SA/NSA), перспективные модели 6G; Wi-Fi 802.11ax/be; LoRa/NB-IoT; РРЛ; спутниковые каналы; ВОЛС.

Антенны: SISO, MIMO, Massive MIMO, Beamforming, AAS; импорт 3D-ДН; учёт поляризации и реальных потерь трактов.

### 4.5.6. Многофизическое сопряжение (Co-Simulation)

Обязательны: единый ID сценария, описание входов/выходов решателей, согласование единиц и CRS, синхронизация времени, обнаружение циклических зависимостей, контроль сходимости, обработка ошибок отдельного решателя, фиксация версий, воспроизводимость.

Типовая цепочка:
**мощность → тепловыделение → температура → допустимость работы → доступность комплекса.**

При отсутствии подтверждённой совместимости решателей Система сообщает о невозможности сопряжения; **подмена упрощённым обменом без предупреждения запрещена.**

### 4.5.7. Неопределённость и достоверность

В паспорте расчёта раздельно отражаются:
1. неопределённость исходных данных;
2. численная погрешность;
3. неопределённость параметров модели;
4. ошибка физической модели.

Поддержка: анализ чувствительности, распространение неопределённости, интервальные оценки, Монте-Карло, ранжирование факторов, перечень параметров, требующих дополнительного измерения.

> **Запрет ложной точности:** большое число десятичных знаков не компенсирует неточные исходные данные.

### 4.5.8. Суррогатные модели

Допускаются полиномиальные аппроксимации, гауссовские процессы, RBF, редуцированные и нейросетевые модели. Обязаны: обучение на проверенных расчётах, хранение обучающего набора, оценка ошибки, область применения, детекция выхода за обучающий диапазон, сравнение с основным решателем, повторная проверка после переобучения, возможность отключения.

> Суррогат **не приравнивается** к физическому решателю и всегда маркируется.

### 4.5.9. Реестр математических моделей

Для каждой модели хранятся: ID, назначение, математическое описание, класс оборудования, входы/выходы, единицы, метод, версия реализации, обязательные данные, диапазоны, допущения, точность, эталонные сценарии, результаты V&V, зависимости от библиотек, аппаратные требования, лицензия, статус допуска, дата проверки, ответственное лицо, история изменений.

**Статусы:** `Разрабатывается`, `Проверяется`, `Валидирована для указанной области`, `Ограниченно применима`, `Выведена из эксплуатации`.

### 4.5.10. Паспорт расчётного запуска

Каждый запуск фиксирует: ID запуска, ID и версию модели, хэши и версии входных данных, паспорт оборудования, параметры точности, CRS и единицы, вычислительную среду (CPU/GPU, библиотеки), время, статус, предупреждения, оценку применимости, ссылки на результаты и протокол проверки.

**MOD-002.** Повторный запуск на сохранённом снимке данных даёт результат в установленных допусках. Расхождения CPU/GPU проверяются относительно допуска.

**MOD-003.** При выходе за область применимости Система формирует предупреждение или блокирует расчёт — но не выдаёт результат как достоверный.

### 4.6.2. Многослойная модель

Геометрический · конструкционный · функциональный · электрический/энергетический · радиотехнический · сетевой · программный · эксплуатационный · измерительный · расчётный · документальный · исторический слои. Каждый слой имеет собственную версию и статус подтверждения при общем ID объекта.

### 4.6.3. Правила обновления

- Телеметрия обновляет **наблюдаемое** состояние.
- Утверждённая базовая конфигурация **не изменяется автоматически**.
- Измерение, отличное от паспортного значения, хранит **оба значения** с датой, средством измерения, методикой, погрешностью, статусом поверки и ответственным.
- Выброс не считается ошибкой автоматически: решение об отбраковке основано на методике и фиксируется.
- Прогноз маркируется как оценка с горизонтом, основаниями и неопределённостью.

### 4.6.4. Идентификация и калибровка

Поддержка: метод наименьших квадратов, нелинейная идентификация, байесовская оценка, анализ чувствительности, доверительные интервалы, сравнение альтернативных моделей.

**Обязательно:** раздельное хранение паспортных и идентифицированных параметров; указание обучающих данных; проверка на независимом наборе; запрет автоматического изменения базовой линии; сообщение о невозможности надёжно оценить параметр при недостаточной информативности.

## 4.7. Сценарное моделирование воздействий и устойчивости

### 4.7.1. Сквозная цепочка

**Событие → изменение состояния объекта → отказ/деградация → влияние на услуги → обнаружение → локализация → восстановление → остаточная работоспособность.**

### 4.7.2. Классификатор воздействий

| Класс | Моделируется | Результат |
|---|---|---|
| Механическое / конструкционное | Повреждения, деформации, нарушения креплений | Состояние конструкции, потеря функций, необходимость обследования |
| Тепловое / пожарное | Перегрев, распространение тепла, отказ охлаждения | Температурные ограничения, отключения, время восстановления |
| Электромагнитное / РЭБ | Помехи, интерференция, чувствительность устройств | SINR, ошибки, доступность канала |
| Электроснабжение | Пропадание питания, переключение, разряд АКБ, отказ ИБП | Автономность, остаточный ресурс, время до потери функции |
| Информационное / кибернетическое | Отказ ПО, нарушение целостности, потеря синхронизации | Затронутые функции и зависимые системы |
| Связность инфраструктуры | Повреждение линий, отказ узлов | Потерянные связи, изолированные сегменты |
| Природное / климатическое | Ветер, осадки, обледенение, затопление, пыль | Ограничения эксплуатации, деградация |
| Логистическое / эксплуатационное | Недоступность объекта, дефицит ЗИП, задержка | Увеличение срока восстановления |
| Комбинированное / каскадное | Совместные эффекты, общие причины отказов | Суммарные последствия, критические зависимости |

**Запрещено** объединять разнородную физику одним универсальным алгоритмом. Объединение выполняется на уровне общей модели состояния и последствий.

### 4.7.3. РЭБ и устойчивость радиосвязи

Модель учитывает: радиоканал (уровень, шумы, замирания, чувствительность), радиосредство (диапазон, полоса, режимы), АФУ (потери, состояние), сеть (резервирование, загрузка), навигацию и синхронизацию (альтернативные источники), мониторинг спектра.

Режимы: штатная обстановка → повышенные помехи → переменная помеха → потеря канала → нарушение синхронизации → восстановление.

**Раздельные протоколы:** физическое воздействие (изменение параметров канала) и системная устойчивость (какие услуги сохранены).

> Программная оценка **не заменяет** полигонные испытания и не является утверждением «защищённости от РЭБ».

### 4.7.4. Разведзащищённость и наблюдаемость

Раздельные модели признаков:
- радиоэлектронная наблюдаемость;
- визуальная;
- тепловая;
- информационная;
- поведенческая (на агрегированных данных).

Для каждого сенсорного канала задаются: признак, характеристики и ограничения сенсора, условия наблюдения, фон, качество данных, порог регистрации, критерии **обнаружения / классификации / идентификации**, неопределённость.

**Результаты раздельны:** «признак потенциально наблюдаем» / «обнаружение оценено моделью» / «подтверждено измерением».

### 4.7.5. Маскировка как многокритериальная задача

Сравнение вариантов по: визуальному, тепловому, электромагнитному, конструкционному, эксплуатационному, функциональному и экономическому критериям.

**Вариант допустим только при соблюдении обязательных ограничений** по безопасности, теплоотводу, ЭМС, прочности и функциональности. Снижение заметности ценой нарушения ограничения не является улучшением.

### 4.7.6. Повреждения и восстановления

Классы состояний: конструкционное, электрическое, кабельное, радиотехническое, программное, комплексное.

Система различает: **предполагаемое повреждение → результат расчёта → фактическое обследование → подтверждение исправности после ремонта.**

Модель восстановления учитывает: диагностику, квалификацию и доступность персонала, ЗИП, доставку, допуск, последовательность работ, ограничения параллельности, **повторную верификацию конфигурации после ремонта**.

### 4.7.7. Показатели

Доступность · время восстановления · остаточная функциональность · время автономной работы · доля успешных сценариев · потребность в ресурсах · неопределённость · время обнаружения · время локализации · сохранность конфигурации · готовность к восстановлению.

Для вероятностных показателей публикуются число прогонов, доверительные интервалы и параметры генератора сценариев.

## 4.8. Управление конфигурацией, жизненным циклом и испытаниями (CFG / TST)

### 4.8.1. Базовая конфигурация фиксирует

Проект · ГИС-основу · объекты инфраструктуры · оборудование · математические модели · расчёты · документацию · результаты испытаний · цифровые двойники.

### 4.8.2. Процесс изменения

```
Регистрация предложения и причины
        ↓
Анализ зависимостей (граф)
        ↓
Оценка последствий: какие расчёты, документы, испытания затронуты
        ↓
Подготовка новой версии
        ↓
Согласование уполномоченными лицами
        ↓
Повторные расчёты и контрольные испытания
        ↓
Утверждение новой базовой линии ИЛИ отклонение
        ↓
Архивирование предыдущей версии с сохранением воспроизводимости
```

**Ключевое правило:** изменение параметра не подменяет исходные данные выполненного расчёта. Старый результат сохраняется со своей конфигурацией; новый получает собственный ID.

### 4.8.3. Инженерные правила

Правила проверки хранятся **отдельно от кода**, имеют ID, версию, автора, основание, дату ввода, класс замечания (блокирующее / критическое / предупреждение / рекомендация) и протокол проверки.

Изменение правила не изменяет задним числом результаты утверждённых проектов.

### 4.8.4. Испытательная база и метрология

- Реестр стендов, приборов и испытательного оборудования.
- Паспорта СИ, сроки поверки/калибровки, статус.
- Привязка протокола к прибору, методике, версии испытательного ПО и конфигурации изделия.
- Первичные и обработанные результаты; условия испытаний; отступления от методики.

> Если СИ не соответствует условиям применения, Система предупреждает о **недопустимости использования его результатов** для подтверждения требования.

### 4.8.5. Цифровой паспорт испытания

ID · объект · конфигурация · основание (требование, ПМИ) · условия · оборудование · результаты · отклонения · заключение и статус согласования.

### 4.8.6. Замечания

Для каждого замечания: ID, источник, описание, связанное требование, критичность, ответственная организация, мероприятия, затронутые документы и компоненты, повторная проверка, основание закрытия.

**Статусы не взаимозаменяемы:** `Устранено` → `Проверено` → `Согласовано` → `Закрыто`.

**Особенно важно для ВТ-02:** наличие всех файлов в Системе **не означает** выполнения этапа контракта. Этап закрывается только решением уполномоченного органа.

**Особенно важно для ВТ-05:** Система выдаёт **оценку формальной готовности**, а не подменяет комиссию.

## 4.10. ИИ-слой (AI)

### 4.10.1. Разрешённые функции

- Разбор ТЗ с извлечением требований, указанием источника и уверенности.
- Поиск неполных исходных данных и зависимостей.
- Ответы со ссылками на документы, версии моделей и нормативные основания (локальный RAG).
- Объяснение ошибок топологии и совместимости.
- Подготовка черновиков отчётов с прослеживаемостью до данных.
- Предложение допустимых сценариев и параметров.
- Поиск противоречий и подозрительных значений.
- Обучение на синтетических наборах.
- Построение суррогатных моделей и анализ аномалий.

### 4.10.2. Обязательные ограничения

| Запрет |
|---|
| ИИ не изменяет утверждённую конфигурацию |
| ИИ не подтверждает техническую исправность |
| ИИ не объявляет модель валидированной |
| ИИ не закрывает замечания и не утверждает документы |
| ИИ не подменяет расчётное ядро |
| Корреляция не выдаётся за причинно-следственную связь |
| Прогноз без независимой проверки не выдаётся за достоверный |

Каждый ответ содержит: источники, версии, допущения, ограничения, статус подтверждения. При недостатке данных ИИ **запрашивает данные или объявляет неопределённость**.

### 4.10.3. Автономность ИИ

Локальное хранение весов, токенизаторов, индексов и векторных представлений. Отсутствие внешней авторизации и облачных API. Документированные аппаратные требования к каждой модели. **Отключение ИИ не нарушает работу ГИС и инженерного ядра.**

## 4.11. Геймификация, обучение и инженерный полигон

### 4.11.1. Принцип

> Игровой элемент выдаётся **за проверяемый результат**, а не за нажатие кнопки.

Геймификация не заменяет инженерный контроль, верификацию и утверждение.

### 4.11.2. Архитектура

```
Инженерные модули + Каталог + Проверки и испытания
                 ↓
            Шина событий
                 ↓
        Движок правил геймификации
                 ↓
 Достижения / Обучение / Командная панель
                 ↓
             Журнал аудита
```

Правила настраиваются независимо от ядра. Визуальные награды отключаются без потери инженерной функциональности.

### 4.11.3. За что начисляются баллы

Подтверждённое выполнение требований; устранение конфликтов совместимости; повышение качества данных; корректная топология; подтверждённое резервирование; воспроизводимость; документирование допущений; закрытие замечаний после повторной проверки.

### За что начислять запрещено

Количество объектов без качества · запуск расчёта без анализа · сокрытие дефектов · обход согласования · скорость ценой точности или безопасности · неподтверждённые результаты.

Предусмотрены: защита от повторного начисления, отзыв ошибочно начисленных баллов с объяснением, журналирование корректировок.

### 4.11.4. Инженерный полигон — 8 этапов

1. Постановка задачи
2. Разведка исходных данных
3. Проектирование архитектуры
4. Сборка цифрового двойника
5. Инженерное моделирование
6. Проверка сценариев
7. Сравнение вариантов
8. Защита проекта

Переход определяется **инженерными критериями**, а не количеством очков.

### 4.11.5. Независимые индикаторы

Бюджет · уровень резервирования · доля объектов с требуемой связностью · полнота документации · стоимость · готовность.

> Высокий суммарный процент **не компенсирует** нарушение обязательного требования.

### 4.11.6. Учебные миссии

«Собери узел» · «Найди ошибку в паспорте» · «Проверь модель» · «Безопасное изменение» · «Восстанови состояние» · «Восстанови ОШС» · «Проведи инвентаризацию» · «Диагностируй состояние» · «Подготовь ТО».

Учебный режим работает на изолированных синтетических данных с трёхуровневыми подсказками и объяснением **почему результат верен**.

### 4.11.7. Уровни компетенции

0 Исследователь → 1 Компоновщик → 2 Проектировщик → 3 Инженер-расчётчик → 4 Инженер-верификатор → 5 Руководитель проекта.

**Уровень пользователя и зрелость проекта — разные показатели.**

### 4.11.8. Индексы готовности ЦД

Раздельно: полнота данных · достоверность · зрелость модели · совместимость · эксплуатационная готовность.

Не рассчитанный показатель отображается как **«не определён»**, а не 0 % или 100 %.

## 4.12. Уведомления и события (NTF)

### 4.12.1. Два канала единой шины

- **Popup** — реакция «здесь и сейчас»: Toast, Inline Alert, Modal Dialog, Critical Alert, Progress Popup.
- **Push** — центр уведомлений рабочего пространства с фильтрами и действиями.

### 4.12.2. Жизненный цикл

`Создано → В очереди → Доставлено → Просмотрено → Подтверждено → Исполнено → Закрыто`

> Доставка **не равна** просмотру; просмотр **не равен** исполнению. Уведомление не является подтверждением изменения данных.

### 4.12.3. Обязательные механизмы

- Уникальный ID и временная метка события.
- Дедупликация и группировка связанных событий.
- Эскалация необработанных критических событий по правилам администратора.
- Локальная очередь при недоступности клиента; доставка после восстановления без лавины дубликатов.
- Переход к объекту с **повторной проверкой прав доступа**.
- Запрет раскрытия защищённых сведений в превью и внешних каналах.
- Запрет бесследного отключения критических уведомлений пользователем.

### 4.12.4. Каталог событий

Критическое несоответствие ограничениям · неисправность оборудования · срок ТО · устаревшие/неподтверждённые данные ОШС · конфликт совместимости · завершение/ошибка расчёта · изменение исходных данных ЦД · назначение задачи · документ на согласование · завершение испытания · новая учебная миссия · ошибки импорта · сбой резервного копирования.

## 4.13. Управление требованиями и данными (REQ / DAT)

### 4.13.1. Реестр требований

Каждому требованию присваивается постоянный ID вида `ПРЕФИКС-NNN`. При изменении формулировки сохраняются история, автор, основание, дата и повторная проверка.

### 4.13.2. Матрица прослеживаемости

**Прямая:** требование → компонент → данные и версии → тест → протокол → решение.

**Обратная:** модуль / модель / набор данных → требования, ради которых они созданы.

> Требование не считается подтверждённым наличием пункта в интерфейсе.

### 4.13.3. Управление качеством данных

Система проверяет: обязательность, типы, диапазоны, согласованность связанных параметров, дубликаты, конфликты, источники, сроки актуальности, ссылки.

**Статус качества данных не подменяет техническое состояние объекта.**

### 4.13.4. Миграция

Инвентаризация источников → пробный перенос на репрезентативной выборке → контроль полноты и качества → протоколирование → повтор без повреждения исходного архива.

**Исходные файлы и сведения об их происхождении остаются неизменными.**

### 4.13.5. Архив воспроизводимости

Для утверждённых проектов формируется пакет: данные, версии моделей, настройки, допущения, результаты, документы, необходимые библиотеки. Пакет обеспечивает воспроизведение результата в будущих версиях Системы.

## 4.14. Интеграции и API (INT)

Обязательны: версионирование API и схем; валидация структуры и типов; идемпотентность; контроль дублирования; регистрация успешных и неуспешных обменов; повторная обработка; контроль доступа на уровне операций и объектов; сохранение ID и происхождения; обнаружение несовместимости.

**Контракт интерфейса содержит:** назначение и владельца, операции, схемы запроса/ответа, обязательные поля, форматы дат и единиц, аутентификацию, обработку ошибок, журналирование, ограничения производительности, правила совместимости, корректные и некорректные примеры сообщений.

## 4.15. Эксплуатация и мониторинг (OPS)

- Локальная панель состояния сервисов, СУБД, GPU, очередей и хранилищ.
- Контроль зависших и ошибочных заданий, повторный запуск.
- Структурированные журналы, трассировка запросов, диагностический отчёт.
- Резервное копирование с проверкой восстановления и целостности связей.
- Регламент обновления и отката.
- **Запрет передачи диагностических данных за пределы контура по умолчанию.**

# 6. ЕДИНАЯ ИНФОРМАЦИОННАЯ МОДЕЛЬ

## 6.1. Принципы

1. **Устойчивый идентификатор** создаётся один раз и не переиспользуется после списания.
2. Переименование, смена владельца или координат **не создаёт** новый объект.
3. Модель оборудования, экземпляр и паспорт — **разные сущности**.
4. При импорте сохраняются внешний ID, источник и результат сопоставления.
5. Слияние дубликатов не выполняется автоматически и необратимо.
6. Архивирование сохраняет исторические связи.

Для каждого норматива фиксируются:

- метрика и единицы измерения;
- порог и допустимое отклонение;
- длительность и число повторов;
- условия холодного / прогретого кэша;
- способ измерения и место хранения протокола.

**Профили нагрузки:**

| S4 — высокодетальный | Полная 3D-физика, максимальная точность |

## 7.3. Отказоустойчивость и контролируемая деградация

- При отказе GPU или вычислительного узла задание сохраняется, восстанавливается или безопасно перезапускается.
- При нехватке ресурсов Система отключает необязательные функции (высокий LOD, фоновый ИИ), сохраняя базовое редактирование и 2D.
- **Запрет тихой деградации:** если точный расчёт невозможен, Система сообщает об этом, а не молча подменяет его упрощённым.
- После перезапуска проекты, очереди и журналы сохраняются.

## 7.4. Переносимость

Подтверждаются отдельными протоколами для: x86-64; ARM; Эльбрус; Astra Linux Special Edition; Windows; серверных и рабочих GPU-конфигураций.

**Гарантия одинаковой производительности на всех платформах не предполагается.**
