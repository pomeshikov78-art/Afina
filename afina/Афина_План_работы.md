## 1. Общая схема работ

Работа ведётся в двух сопряжённых треках:

1. **Трек П — прототипирование интерфейса и UX-семантики** (быстрые итерации, HTML-прототипы, валидация сценариев ТЗ на кликабельных макетах).
2. **Трек Р — разработка рабочей программы** (рубежи G0–G5 по ТЗ §12: архитектура, ядро, подсистемы, испытания, поставка).

Принцип: каждый прототип (трек П) проверяет требования интерфейса (§10) и информационную семантику (§1.5, §4, §6) до вложения ресурсов в код (трек Р). Прототипы версионируются: каждая версия сохраняется отдельным файлом `Афина_vN.html` и не перезаписывает предыдущую.

```
Трек П:  v0 (7 концептов) → v1 (рабочее ядро UI) → v2 (расширение) → v3… (детализация)
              │                    │                     │
              ▼                    ▼                     ▼
Трек Р:  ── G0 обоснование ── G1 реализуемость ── G2 базовое ядро ── G3 ── G4 ── G5 ──
```

### 2.2. Этап П-1 — версия v1: рабочее ядро интерфейса ✅ ВЫПОЛНЕНО

**Файл:** `Афина_v1.html` (= `app/index.html`).

**Ходы этапа:**
1. Каркас v6 развёрнут в полноценное SPA-приложение: 10 модулей с навигацией (Сцена/ГИС, Каталог КСИМ-ДД, Расчёты ENG6+, Двойники, Сценарии, ОШС, RTM, Данные, Уведомления, Параметры).
2. Контекстный инспектор: правая панель меняется под активный модуль.
3. ИИ-панель: чат с быстрыми командами; ответы с источниками, версиями и блоком ограничений (AI-001, п. 4.10.2); сворачивание в плавающую кнопку.
4. Модальные окна: «Паспорт расчёта» (§4.5.10, MOD-002/005), «Мастер создания средства» (§4.3.6, валидация при вводе, EQP-001).
5. Сценарий воздействий: 7 классов, пошаговая анимация цепочки «событие → … → остаточная функциональность» (§4.7.1), Монте-Карло с ДИ (§4.7.7).
6. Уведомления: центр NTF с полным жизненным циклом из 7 статусов (§4.12.2), popup-тосты, эскалация критических.
7. Данные: конфликты с битемпоральностью (§6.3), арбитраж без перезаписи (DAT-004), качество данных (KPI ≥ 98 %).
8. Автономность: режим Б, переключение режима заблокировано по роли с записью в аудит (AUT-003, SEC-005), счётчик внешних соединений = 0.

**Результат:** кликабельный прототип, демонстрирующий ~60 % интерфейсных требований ТЗ.

### 2.3. Этап П-2 — версия v2: расширение модулей ✅ ВЫПОЛНЕНО

**Файл:** `Афина_v2.html` (152 КБ, единый файл, офлайн).

**Ходы этапа:**
1. **Drag-and-drop из каталога на сцену** (3DM-002/003/004/005): перетаскивание карточек, snap-to рельефу, проверка сервисных зон с отказом и объяснением причины, двухуровневый отклик (Preview сразу → точный расчёт в очередь → паспорт ENG-001), отрисовка размещённых объектов с маркировкой «предварительно».
2. **Модуль «Замечания»** (§4.8.6, TST-003): реестр с критичностью и ответственными организациями; карточка замечания (все обязательные поля); цепочка статусов «Устранено → Проверено → Согласовано → Закрыто» с реальной проверкой Maker–Checker (верификатор не может согласовать собственное устранение — отказ логируется, SEC-005).
3. **Модуль «Инженерный полигон»** (§4.11): 8 этапов с инженерными критериями перехода (не очки), XP только за проверяемые результаты + пример отзыва баллов, перечень запретов начисления, учебные миссии, уровни компетенции 0–5, независимые индикаторы (включая «не определён» вместо 0/100 %).
4. **Модуль «ВТ-профиль»** (§4.9): ВТ-01…ВТ-08, контрольные события этапа ГОЗ (ВТ-02: готовность изделия ≠ закрытие этапа), четыре уровня готовности к предъявлению (ВТ-05: оценка формальной готовности, не замена комиссии), EOL-риски (ВТ-07).
5. **Светлая/тёмная тема** (переключатель в тулбаре), «Настроить панель» (§10.3).

**Проверенные требования:** 3DM-002…005, ENG-001, ENG-006, SEC-005, TST-003, §4.8.6, §4.9, §4.11, §10.3.

## 4. Порядок работы на каждой итерации (регламент)

1. **Вход:** список задач итерации со ссылками на ID требований ТЗ.
2. **Разработка:** реализация; каждая функция сопровождается записью в RTM (требование → компонент → тест).
3. **Самопроверка:** юнит- и интеграционные тесты; для расчётных модулей — эталонные сценарии Приложения Е.
4. **Верификация:** независимая проверка (другой субъект — Maker–Checker).
5. **Фиксация версии:** нумерованный артефакт (`Афина_vN.html` для прототипов; релизные теги для кода), журнал изменений (раздел 6).
6. **Демонстрация заказчику:** сценарный прогон, а не показ кнопок.
7. **Выход:** протокол итерации, обновлённые реестры (требований, замечаний, рисков).

**Правило статусов:** «реализовано» ≠ «принято». Требование считается подтверждённым только после проверки по утверждённому критерию (ТЗ §11.2, §12.1).
