## 1. Назначение и границы алгоритма

**ENG6-PLAN** решает задачу *синтеза плана развертывания системы связи*: по заданной
тополографии-кандидату, парку техники и заявкам на ресурсы алгоритм формирует
**три выходных артефакта**:

1. **распределение ресурсов** — какие единицы техники развернуть и на каких позициях,
   какие линии активировать, как нарастить ёмкость в пределах бюджета;
2. **маршруты** — пути передачи для каждой заявки с выделенной полосой, задержкой
   и запасом по уровню сигнала;
3. **расписание развертывания** — волны работ с учётом иерархии ОШС, времени марша
   и ограничения на число одновременных бригад.

**Границы.** Алгоритм не выполняет: расчёт электромагнитной совместимости (ЭМС) и
помеховой обстановки в полном объёме (это делает ENG6 в режиме перекрёстной проверки,
п. 9), планирование частотных присвоений, материально-техническое обеспечение.
Ядро **изолировано**: не имеет доступа к БД, сети, файловой системе и DEM-сервисам
(требование «Айтишника»); рельеф — синтетический или плоский.

## 2. Входные данные

### 2.1. Топология (граф-кандидат)

Задаётся парой `G_c = (V, E_c)`:

* `V = {v_1 … v_n}` — позиции размещения (узлы). Каждый узел:
  `id`, `type ∈ {cp, relay, radio, sat, observer, ew_jam, ew_rlr, ew_rer}`,
  координаты `(lat, lng)` в WGS-84 с точностью 6 знаков (NFR-03, ≈ 0,11 м),
  `status ∈ {active, planned, failed}`, `parentId` (иерархия ОШС),
  радиопараметры `(P_tx [дБм], G_tx [дБи], G_rx [дБи], P_sens [дБм], h [м], f [МГц], L_f [дБ], NF [дБ], mobility)`;
  при отсутствии параметров подставляются пресеты `ENG6.NODE_PRESETS[type]`.
* `E_c = {e_1 … e_m}` — потенциальные линии. Каждая:
  `id`, `from`, `to`, `type ∈ {VHF, UHF, HF, RRL, SAT, FOC}`,
  `(f, B, mod, fec)`, `priority ∈ [1;5]`, `isBackup`, `cost` (при отсутствии —
  из таблиц `DEFAULT_LINK_COST[type] + DEFAULT_LINK_COST_PER_KM[type]·d`).

Число рёбер **не ограничено** сверху требованием полноты: `E_c` задаёт заказчик,
а физический допуск (п. 4) отбраковывает недостижимые направления.

### 2.2. Парк техники (ресурсы)

`U = {u_1 … u_p}`: `unitId`, `kind`, `nodeType`, `condition ∈ {green, yellow, red}`,
`costDeploy`, `deployTimeMin`, `powerW`, `note`.

Правила (FR-RES-03):
* `red` — размещение **запрещено** (узел исключается из графа, статус `UNIT_NOT_READY`),
  если не задано `constraints.allowRedUnits = true`;
* `yellow` — размещается с деградацией тракта `−3 дБ` (настраивается) и предупреждением;
* привязка «узел ↔ единица техники» — 1:1; явная привязка (`node.unitId`) имеет приоритет;
* нехватка единиц типа `t` фиксируется как `UNIT_SHORTAGE{t: count}`.

### 2.3. Заявки на ресурсы

`D = {d_1 … d_K}`: `from`, `to` ∈ V, `rateKbps > 0`, `maxDelayMs`, `maxHops`,
`priority ∈ [1;5]` (**1 — наивысший**), `minAvailabilityPct`, `protected` (требование
двух непересекающихся путей).

### 2.4. Ограничения

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `budget` | предельная суммарная стоимость, у.е. | ∞ |
| `minMarginDb` | минимальный запас по уровню (порог демодуляции) | 3 дБ |
| `maxDelayMs` | предельная односторонняя задержка | 250 мс |
| `maxHops` | предельное число ретрансляций | 8 |
| `reserveFactor` | коэффициент резервирования ёмкости | 1,3 |
| `maxSimultaneousDeploy` | число одновременных бригад (C) | 4 |
| `crewSpeedKmh` | скорость марша (для расписания) | 40 км/ч |
| `maxUtilizationPct` | порог загрузки канала для замечания | 85 % |
| `requireRedundancy` | требовать резервирование всех заявок | false |
| `physics` | `fast` / `full` / `auto` | auto |
| `timeLimitMs` | жёсткий лимит времени расчёта | 30 000 мс |
| `frameKbit` | размер кадра для задержки сериализации | 1 кбит |
| `hopProcessingMs` | задержка обработки на ретрансляторе | 2 мс |

### 2.5. Веса целевой функции и среда

`weights = {cost, delay, survivability, margin}` (нормируются к сумме 1);
`environment = {clutterType, weather, ionosphere, terrain, miscLossDb}` — параметры
среды ENG6 (тип местности задаёт показатель `n` и σ замираний, погода — затухание
в дожде/тумане/газах, ионосфера — применимость КВ).

## 3. Выходные данные

```
{ status, statusReasons[], plan{ deployedUnits[], activeLinks[], routes[],
  schedule{waves[], makespanMin, criticalPath}, rejectedLinks[], survivability{} },
  metrics{}, diagnostics{ issues[], recommendations[], infeasibility{causes[],
  disconnectedComponents[], minimalRelaxations[], partialSolution}, approximation{} },
  timings{}, core{ engine, version, sha256, physics } }
```

**Статусная модель** (требование Критика — «не падать с OutOfMemory, а возвращать
статус Infeasible и предлагать частичное решение»):

| Статус | Условие |
|---|---|
| `OPTIMAL` | все заявки обслужены **и** стоимость активации ≤ нижней оценки задачи Штейнера (доказуемая оптимальность в принятой модели) |
| `FEASIBLE` | все заявки обслужены, оптимальность не доказана |
| `PARTIAL` | обслужена часть заявок (или не выполнено резервирование/бюджет) |
| `INFEASIBLE` | не обслужено ни одной заявки при заданных ограничениях |
| `INVALID` | вход не прошёл валидацию (расчёт не запускался) |
| `TIMEOUT` | исчерпан `timeLimitMs` — возвращено частичное решение |
| `ERROR` | внутреннее исключение (фиксируется в журнале аудита) |

Для `PARTIAL`/`INFEASIBLE` **обязательно** заполняется
`diagnostics.infeasibility`:
* `causes[]` — коды причин (`NET_DISCONNECTED`, `BUDGET_EXCEEDED`, `CAPACITY_SHORTAGE`,
  `DELAY_UNREACHABLE`, `UNIT_SHORTAGE`, `LINK_REF_BROKEN`, …);
* `disconnectedComponents[]` — состав компонент с размерами, идентификаторами и центроидами;
* `minimalRelaxations[]` — **численные** послабления: `ADD_RELAY{at:{lat,lng}, spanKm, requiredEirpDbm}`,
  `RAISE_BUDGET{value}`, `RELAX_MAX_DELAY_MS{value}`, `ADD_CAPACITY{linkId, value}`;
* `partialSolution` — что всё-таки построено (заявки, полоса, стоимость, линии, узлы).

## 4. Физический уровень (модель канала)

Для каждого ребра `e = (u,v)` вычисляются: длина `d_e` (гаверсинус, R = 6371 км —
побайтово та же формула, что в ENG6), потери трассы `PL_e`, уровень приёма,
запас, SNR/SINR, пропускная способность, задержка, доступность.

**Режим `full`** — дословный вызов `ENG6.calcLink()`: профиль рельефа (25/50/100
отсчётов), дифракция на ножевом крае по ITU-R P.526 с суммированием Эпштейна–Петерсона
(кап 40 дБ), зона Френеля, дождь ITU-R P.838-3, газы P.676, цепочка моделей
(замирания/MIMO/MODCOD/информационные/телетрафик), РЭБ, BER/FER.

**Режим `fast`** — те же функции ENG6 (`PROP.hata`, `PROP.fspl`, `PROP.logDistance`,
`PROP.twoRay`, `PROP.rainGamma`, `PROP.gasGamma`, `PROP.fogGamma`, `CLUTTER`,
`noiseDbm`, `practicalRate`, `shannonKbps`, `HF.analyse`, `SAT.slantKm`, `FIBER.loss`),
вызванные напрямую, **без** профиля рельефа и цепочки моделей:

* УКВ/ДМВ: дальняя зона `d > 4·h_t·h_r/λ` и LOS → `min(Hata_open, two-ray)`,
  иначе `logDistance(d, f, n_clutter)` — дословно ветвь `quality='balanced'` оригинала;
* РРЛ: `FSPL` (+ требование LOS);
* КВ: `FSPL + A_ионосф + 25 дБ` (по `HF.analyse`: MUF/LUF/ПМПЧ, применимость);
* СПУТНИК: наклонная трасса ГСО, `FSPL + дождь + газы + туман`;
* ВОЛС: `0,22 дБ/км + муфты (1/4 км) + разъёмы`, задержка `4,9·L + 1` мс.

Ключевые соотношения:

```
N      = −174 + 10·lg(B_кГц·10³) + NF                       [дБм]   (ENG6.noiseDbm)
SNR    = P_rx − N,  P_rx = P_tx + G_tx + G_rx − PL_Σ
margin = SNR − reqSNR,   reqSNR = reqSNR(mod) − gain(fec)     ← СЕМАНТИКА ENG6
sensMargin = P_rx − P_sens                                    (отдельное поле)
C_theor = B·log2(1 + 10^(SNR/10))                             [кбит/с] (Шеннон)
C_pract = B·bits(mod)·rate(fec)·0,85  (адаптивный MODCOD-ладер) [кбит/с]
A      = Φ(margin / σ_clutter)                                 (логнормальное затенение)
```

> **Важно.** `marginDb` в ENG6 — это запас относительно **порога демодуляции**
> (`SINR − reqSNR`), а не относительно чувствительности приёмника. Расхождение
> семантик на 6…12 дБ было обнаружено при сверке режимов и устранено
> (см. `docs/06_DEFECTS.md`, DEF-02). Оба значения присутствуют в ответе.

**Компенсация отсутствия рельефа в `fast`:** в `PL_Σ` добавляется
`fastMarginPenaltyDb` (по умолчанию 6 дБ). Знак расхождения известен:
дифракция только увеличивает потери, поэтому `fast` **оптимистичнее** `full`
на пересечённой местности. Тест `physics fidelity` фиксирует: на плоском рельефе
расхождение режимов < 0,01 дБ по запасу, ёмкости и задержке; на синтетическом
рельефе (амплитуда 120 м) — до 40 дБ, что задокументировано как область
применимости `fast`.

**Допуск ребра:** `feasible(e) ⟺ margin_e ≥ minMarginDb ∧ C_pract,e > 0 ∧ τ_e ≤ maxDelayMs ∧ (РРЛ → LOS)`.
Отбраковка сопровождается стабильным кодом (`BELOW_MARGIN`, `OUT_OF_RANGE`,
`CAPACITY_ZERO`, `DELAY_EXCEEDED`, `NO_LOS_REQUIRED`, `UNIT_NOT_READY`, `FORBIDDEN_TYPE`, …)
и гистограммой в ответе.

## 5. Математическая постановка

### 5.1. Переменные

| Переменная | Тип | Смысл |
|---|---|---|
| `x_u ∈ {0,1}` | целочисл. | развернуть единицу техники `u` |
| `y_e ∈ {0,1}` | целочисл. | активировать линию `e` |
| `f_{k,e} ≥ 0` | непрерывн. | полоса заявки `k` на ребре `e`, кбит/с |
| `z_e ∈ {0,1}` | целочисл. | модернизация ёмкости ребра `e` (фаза 6.5) |
| `t_j ≥ 0` | непрерывн. | момент начала работ по объекту `j`, мин |
| `c_b ≥ 0` | непрерывн. | момент освобождения бригады `b` |

Рабочий граф `G = (V, E)` — подграф `G_c` на допустимых рёбрах:
`E = {e ∈ E_c : feasible(e)}`, ёмкость `C_e = C_pract,e / reserveFactor`.

### 5.2. Ограничения

**(1) Сохранение потока** для каждой заявки `k = (s_k, t_k, r_k)`:

```
Σ_{e∈δ⁺(v)} f_{k,e} − Σ_{e∈δ⁻(v)} f_{k,e} = { r̂_k, v = s_k;  −r̂_k, v = t_k;  0 иначе }
```
где `r̂_k ≤ r_k` — фактически выданная полоса (частичное обслуживание допускается).

**(2) Ёмкость ребра:** `Σ_k f_{k,e} ≤ C_e·y_e + ΔC_e·z_e`

**(3) Связь активации и потока:** `f_{k,e} ≤ C_e·y_e`

**(4) Развертывание узлов:** `y_e ≤ x_{tail(e)} ∧ y_e ≤ x_{head(e)}`;
`x_u = 0` для техники в состоянии `red` (если `allowRedUnits = false`)

**(5) Бюджет:** `Σ_u costDeploy_u·x_u + Σ_e cost_e·y_e + Σ_e upgradeCost_e·z_e ≤ Budget`

**(6) Задержка:** `Σ_{e∈P_k} (τ_e + τ_hop) + T_ser,k ≤ L_k`,
где `T_ser,k = frameKbit / r̂_k · 1000` мс; опционально `T_queue = Σ_e ρ_e/(1−ρ_e)·T_ser,e`
(модель M/M/1, по умолчанию выключена — на узкополосных каналах ρ→1 даёт
секундные «очереди», физически означающие отказ обслуживания, что уже учтено (2)).

**(7) Число ретрансляций:** `|P_k| − 1 ≤ H_k`

**(8) Доступность:** `Π_{e∈P_k} A_e ≥ minAvailabilityPct_k / 100` (если задано)

**(9) Резервирование** (для `protected` заявок и при `requireRedundancy`):
существуют два реберно-непересекающихся пути `P_k¹, P_k²`; по теореме Менгера
эквивалентно потоку величины 2 при единичных ёмкостях.

**(10) Расписание:**
```
t_j ≥ Σ_{i∈prec(j)} (t_i + deploy_i) + march_j           (иерархия ОШС)
t_j ≥ c_b  для бригады b, назначенной объекту j
c_b ≥ t_j + deploy_j
|{j : t_j ≤ θ < t_j + deploy_j}| ≤ C  для любого момента θ
```

### 5.3. Целевая функция

Минимизировать взвешенную нормированную стоимость решения:

```
F = w_c·Ĉ + w_d·D̂ + w_s·(1 − Ŝ) + w_m·(1 − M̂)  →  min

Ĉ = spent / Budget                     (нормированная стоимость)
D̂ = avgDelay / maxDelayMs              (нормированная задержка)
Ŝ = 0,6·connectivityPct/100 + f(SPOF)   (живучесть)
M̂ = (avgMargin + 10) / 40              (нормированный запас)
```

Результат `F` приводится к оценке `grade ∈ {A ≤ 0,15; B ≤ 0,3; C ≤ 0,5; D ≤ 0,7; F}`.

Задача (1)–(10) является **смешанной целочисленной** (multi-commodity flow с
целочисленными активациями и расписанием) и содержит как частные случаи задачу
Штейнера, 0/1-рюкзак и `R|prec|Cmax` — все NP-трудные. Точное решение для
`n = 10⁵` недостижимо, поэтому применяется декомпозиция (п. 6) с явными
границами приближения.

## 6. Алгоритм решения (декомпозиция на 11 фаз)

| # | Фаза | Метод | Сложность | Гарантия |
|---|---|---|---|---|
| 0 | Валидация | декларативные правила + `ENG6.validateScenario` | O(n+m+K) | мусор не попадает в математику |
| 1 | Назначение техники | пулы по типам с курсорами, `green → yellow` | O(n+p) | детерминированно |
| 2 | Рёбра-кандидаты | дефолты `LINK_TYPES`, стоимости | O(m) | — |
| 3 | Физический слой | `fast` (векторно) / `full` (`calcLink`) | O(m·S), S — отсчёты профиля | см. п. 4 |
| 4 | Допустимый граф | CSR + twin-дуги | O(n+m) | память 24·m + 4·n байт |
| 5 | Связность и каркас | компоненты (итеративный DFS); дерево Штейнера — **2-аппроксимация** (MST на метрическом замыкании, Kou–Markowsky–Berman) | O(n+m) + O(\|T\|·(m+n log n)) | ≤ 2·OPT; при \|T\| > 64 — дерево кратчайших путей (фиксируется в `approximation`) |
| 6 | Маршрутизация | successive shortest paths: Дейкстра по `τ_e + τ_hop + ψ·u_e²` с учётом остаточной ёмкости; порядок — приоритет ↓, полоса ↓, id | O(K·(m + arcs·log n)) | жадность по приоритету; дельта-перевзвешивание O(путь) вместо O(m) |
| 6.5 | Улучшения | 0/1-рюкзак (точное ДП при ≤ 4·10⁶ ячеек, иначе жадность по плотности + swap 1↔2) | O(P·cap) или O(P²) | точность при ДП; ≥ 1/2 OPT для жадности |
| 7 | Резервирование | Дейкстра с запретом рёбер основного пути + проверка мостов активного подграфа | O(K_prot·m log n) | точная проверка 2-связности (Tarjan), поиск пути — эвристика |
| 8 | Живучесть | мосты и точки сочленения (Tarjan, итеративно); min-cut между КП (Dinic) | O(n+m) / O(V²E) | точно; Dinic ограничен `flowMaxArcs` |
| 9 | Расписание | приоритетное списковое расписание (Graham) | O(J log J + J·C) | ≤ (2 − 1/C)·OPT |
| 10 | Метрики и статус | агрегации, LB-проверка оптимальности | O(m+K) | `OPTIMAL` только при `spent ≤ LB` |
| 11 | Кросс-проверка ENG6 | `analyzeScenario` на построенном плане | O(V·E) | только при `nodes ≤ 400 ∧ links ≤ 600` (иначе `SIZE_GUARD`) |

**Нижняя оценка (LB).** `LB = ½·Σ_{t∈T} min_{e∋t} cost_e` — полустепенная оценка
стоимости связывания терминалов. `LB ≤ OPT` всегда; при `spent ≤ LB·(1+10⁻⁹)`
и полном обслуживании заявок статус = `OPTIMAL` (доказуемо оптимально в модели).

**Дедлайн** проверяется между фазами и внутри цикла маршрутизации: при исчерпании
возвращается `TIMEOUT` с уже построенным частичным планом.

## 7. Граничные случаи (обязательное поведение)

| Ситуация | Поведение | Код |
|---|---|---|
| Сеть несвязна | `PARTIAL`/`INFEASIBLE`; компоненты с центроидами; предложение точек установки ретрансляторов с требуемой ЭИИМ (инверсия FSPL) | `NET_DISCONNECTED` + `ADD_RELAY` |
| Заявок больше, чем ёмкости | `PARTIAL`; дефицит по каждой заявке и каждой перегруженной линии; предложение модернизации через рюкзак | `CAPACITY_SHORTAGE` + `ADD_CAPACITY` |
| Бюджета не хватает | обслуживание в порядке приоритета; `RAISE_BUDGET{value}` = точная недостающая сумма | `BUDGET_EXCEEDED` |
| Техники меньше, чем узлов | узлы без техники исключаются; заявки к ним отклоняются | `UNIT_SHORTAGE` / `UNIT_NOT_READY` |
| Нет рёбер / все отбракованы | `INFEASIBLE` + гистограмма причин отбраковки | `NO_LINKS` / `NO_FEASIBLE_LINK` |
| Пустой граф, 0 узлов | `INVALID` (валидатор) | `REQUIRED` |
| Дубликаты id, битые ссылки, `from == to` | `INVALID` с JSON-путями всех ошибок (не более 100) | `DUPLICATE` / `REF` / `CROSS` |
| Превышение лимитов (`maxNodes` и т.п.) | `INVALID` **до** выделения памяти | `LIMIT` |
| 10⁵ узлов | расчёт 47 с, RSS 434 МБ; ответ усекается (`truncation`) с сохранением totals | — |
| Цикл в иерархии ОШС | расписание строится, нарушение фиксируется в `schedule.violations` | — |
| `timeLimitMs` исчерпан | `TIMEOUT` + частичный план | `TIME_LIMIT` |
| Исключение в математике | `ERROR` с кодом, процесс не падает | `CORE_EXCEPTION` |

## 8. Детерминированность (NFR-DET-01)

Один и тот же вход → **побайтово** одинаковый выход (проверяется тестом).
Обеспечивается: сортировкой с полным тай-брейком (приоритет → полоса → id),
отсутствием ГСЧ в маршрутизации, исключением меток времени из ответа
(`timings` — единственный недетерминированный блок; из сравнения исключается),
нормализацией `assumptions` в кросс-проверке ENG6.

## 9. Перекрёстная проверка полным ядром ENG6

Построенный план повторно собирается в сценарий ENG6 и прогоняется через
`analyzeScenario(quality='balanced')`: профиль рельефа, цепочка моделей, РЭБ,
рейтинги `connectivity/throughput/survivability/jamming/recon/redundancy`,
`issues`, `recommendations`. Результат — в `diagnostics.eng6Analysis` с вердиктом:

* `CONSISTENT` — ENG6 подтверждает все активные линии;
* `DEGRADED` — часть линий не проходит полную модель (обычно из-за дифракции в `fast`);
* `REJECTED_BY_ENG6` — план не подтверждён (критическое замечание).

Это независимый контроль качества плана тем же математическим ядром, которое
используется в изделии v8.0.
