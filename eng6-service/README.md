# ENG6-PLAN · Промышленный вычислительный сервис планирования систем связи

Headless-ядро расчёта + REST API + картографический планировщик + нагрузочный
стенд + контейнерная инфраструктура. Реализованы все **5 этапов** технического
задания и **Дополнение к ТЗ №1** (ГОСТ 34.602) с учётом замечаний
«Совещательной комиссии» (Военпред, Айтишник, Критик).

## 1. Быстрый старт

```bash
cd eng6-service

# сервис целиком: UI + API + метрики
node api/main.mjs                 # → http://localhost:8080

# расчёт из командной строки
curl -s -X POST localhost:8080/api/v1/plan/sync \
  -H 'Content-Type: application/json' -H 'X-Requestor: Иванов%20И.И.' \
  --data @examples/battalion.json | jq '.status, .metrics, .plan.schedule.makespanMin'

# тесты, конформанс, нагрузка
npm test                          # 125 тестов (включая исполнение UI в jsdom)
npm run conformance               # протокол ENG6
npm run bench                     # нагрузочный стенд (quick)
npm run bench:full                # то же, до 100 000 узлов (~15 мин)

# контейнер + Prometheus + Grafana
docker build -f deploy/Dockerfile -t eng6-plan:1.0.0 .
docker compose -f deploy/docker-compose.yml up -d --build
```

## 2. Что делает ядро

По заданной топологии-кандидату, парку техники и заявкам на ресурсы ENG6-PLAN
строит **три артефакта**:

1. **распределение ресурсов** — какие единицы техники развернуть, какие линии
   активировать, где нарастить ёмкость в пределах бюджета;
2. **маршруты** — путь каждой заявки с выделенной полосой, задержкой, запасом,
   доступностью и (по требованию) резервным непересекающимся путём;
3. **расписание развертывания** — волны работ с учётом иерархии ОШС, времени
   марша и ограничения на число одновременных бригад.

Плюс диагностика: статус (`OPTIMAL/FEASIBLE/PARTIAL/INFEASIBLE/INVALID/TIMEOUT/ERROR`),
причины невыполнимости, **численные послабления** (где поставить ретранслятор и
какая ЭИИМ нужна, на сколько поднять бюджет, на сколько нарастить ёмкость линии),
частичное решение, живучесть (ЕТО, мосты, min-cut), перекрёстная проверка плана
полным ядром ENG6.

Полная математическая постановка — [`docs/01_MATH_MODEL.md`](docs/01_MATH_MODEL.md).

## 5. Ответы на замечания комиссии

**🧐 Критик.** «Что, если сеть несвязная? Что, если заявок больше, чем физических
каналов? Алгоритм должен не падать с OutOfMemory, а возвращать статус Infeasible
и предлагать частичное решение».
→ Реализовано буквально: `NET_DISCONNECTED` + компоненты с центроидами +
`ADD_RELAY{at:{lat,lng}, spanKm, requiredEirpDbm}`; `CAPACITY_SHORTAGE` +
дефицит по каждой линии + `ADD_CAPACITY{linkId, value}` + модернизация ёмкости
через 0/1-рюкзак; `INFEASIBLE`/`PARTIAL` всегда содержат `partialSolution`.
Лимиты узлов/рёбер/заявок/тела/памяти проверяются **до** выделения памяти.
Шквал-тест: 60 одновременных тяжёлых задач → 60 × 202, дренаж 6/6, 0 падений,
`429 QUEUE_FULL`/`SYNC_BUSY` при переполнении, `503 MEMORY_BACKPRESSURE` при
исчерпании памяти. Подтверждено тестами и замерами.

**💻 Айтишник.** «Ядро должно быть изолированным. Никаких зависимостей от базы
данных или сети внутри самого алгоритма. Чистая функция: Input Data → Math → Output Data».
→ `plan(request) → response` не мутирует вход (тест), не читает/пишет диск,
не открывает сокетов, не использует `process.env` (кроме флага отладки).
Вендор ENG6 исполняется в отдельном V8-контексте с tripwire на 12 браузерных/сетевых
API (`ENG6_ISOLATION_VIOLATION`), `indexedDB = undefined`, `codeGeneration` отключён.
Отсутствие сетевых/БД-импортов проверяется статическим тестом. Детерминированность:
один вход → побайтово один выход.

**🪖 Военпред.** «Каждый запуск алгоритма должен логироваться: кто запросил,
какие входные параметры (хэш), время старта, время завершения, статус».
→ NDJSON-журнал + кольцевой буфер + `GET /api/v1/audit`. В записи: `ts, event,
mode, taskId, actor, clientId, requestId, inputSha256, inputBytes, sizes,
status, computeMs, queueWaitMs, workerId, resultBytes, httpStatus`. Тела запросов
**не** логируются (только SHA-256 канонического JSON) — координаты являются
охраняемыми данными. В production журнал недоступен без аутентификации.

## 6. Что изменилось относительно исходной постановки

Исходное допущение «файл `comms_planner_v8.0_headless.html` пуст, документацию
ENG6 нужно искать в другом репозитории» **не подтвердилось**: файл содержит
2 551 730 байт и пять скриптовых блоков, включая полное нативное ядро ENG6.
Поэтому ЭТАП 2 начат не «с нуля», а с извлечения и верификации существующей
математики (конформанс 33+5), после чего поверх неё построен планировщик.
Это исключило риск расхождения двух реализаций моделей распространения.
Подробности и все отклонения — `docs/06_DEFECTS.md`.

## 7. Лицензия и назначение

Проприетарно, служебное пользование. Изделие содержит математические модели
радиораспространения (ITU-R P.526/P.838/P.676, Окамура–Хата, two-ray,
логнормальное затенение, Шеннон, BER/FER, модели трафика и замираний) и
предназначено для расчёта систем связи специального назначения; экспортный
контроль и порядок обращения определяются заказчиком.
