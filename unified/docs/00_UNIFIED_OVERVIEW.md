# 00_UNIFIED_OVERVIEW — целевая архитектура совмещённой платформы «Афина»

Дата: 26.10.2026 · Статус: действует (ветка `unified-platform`) · Основание: план совмещения разбора репозитория, раздел 6.

## 1. Принципы

1. **«Афина» — платформа и единая точка входа; ENG6-PLAN — вычислительный контур (sidecar).**
   Платформа владеет данными, ролями, аудитом и паспортами; контур владеет математикой плана.
2. **Один источник истины по математике — вендор ENG6 v5.1.0** (151 модель MLIB, sha256
   `adb610c9…`, конформанс 33+5). Python ENG6+ (10 моделей) — независимый верификатор
   (ARC-002) и резервный путь для режима Б без Node. Вендор не изменяется (§9.3.1 Доп. №2).
3. **Zero-dependency с обеих сторон** — Air-Gap (режим Б) обеспечивается переносом
   бандлов/образов без внешних репозиториев (AUT-T07 доказан для линии A; линия B — образ Docker).
4. **Честность как протокол** — расхождения измеряются и документируются (XVER RAW→ALIGNED),
   статусы требований подтверждаются только тестами/протоколами (RTM 170).

## 3. Потоки данных

### 3.1. Планирование развертывания (основной сценарий)

1. Оператор в клиенте «Афины» собирает обстановку: GEO_OBJECT (позиции), ASSET (парк,
   TECHNICAL_STATE 🟢🟡🔴), ORG_UNIT (ОШС), заявки.
2. Платформа через `bridge/datamodel_map.build_plan_request()` собирает контракт ENG6-PLAN:
   `topology.nodes[]` (parentId — иерархия узлов ОШС; unitId — привязка к парку),
   `topology.links[]` (автовыбор типа по дальности FR-MAP-06 либо явный),
   `fleet[]` (condition green/yellow/red), `demands[]` (rateKbps, приоритеты),
   `constraints`, `environment` (terrain.source=flat|synth до данных заказчика).
3. `bridge/eng6_js_client` выполняет **конформанс-гейт К-04** (33+5; при провале — отказ,
   результат недостоверен и не выдаётся), затем plan/sync (≤500 узлов) или plan/async.
4. Ответ маппится обратно `plan_to_platform_tables()` в плоские таблицы К-03
   (map_object/link_line/link_rejected/route/deployment_wave/schedule_summary/
   survivability/metrics/issues/calc_run) — идентичные выгрузке Пути А, чтобы БД
   заказчика получала одну структуру из обоих источников.
5. Формируется **паспорт запуска ENG-001** с отпечатками обоих вычислительных путей
   (backend: `ENG6-PLAN-service 5.1.0 adb610c9… + ENG6-JS-vendor-probe`), run_id
   связывается с taskId сервиса (единый аудит — шаг 9).

### 3.2. Кросс-верификация (ARC-002, непрерывная)

* Стенд `bridge/xverify.py`: сетка 102 точки внутри доменов MOD-003;
* стадии RAW (фактические расхождения) → ALIGNED (документированные согласования);
* согласования: `COST231 cm_db=+3.0` (ENG6 применяет CM при переданном env),
  `fresnelR ÷ √1000` (единицы вендора); исключение: `hata(suburban)` (вендор трактует
  как urban; для suburb при планировании через ENG6-JS применять env='urban' — консервативно);
* итог 26.10.2026: FSPL и Hata(urban/open) — Δ=0.0 дБ побайтово; ALIGNED PASS.

### 3.3. Режимы эксплуатации

* **Режим А** (автономный контур): platform + engine в ЛВС; TLS на границе; аудит обоих линий.
* **Режим Б** (Air-Gap, одно АРМ): engine поднимается локально (zero-deps), platform — SQLite;
  перенос — бандлы/образы с манифестом sha256 (SEC-002/AUT-T07); внешние соединения запрещены
  (AUT-002/T02 — 0 исходящих, подтверждено протоколами линии A).

## 4. Границы ответственности

| Слой | Владелец данных | Журналирование |
|---|---|---|
| Клиент | состояние сцены — в памяти вкладки (NFR-02: без localStorage) | действия → API платформы |
| Платформа | maître-данные: каталог, ОШС, GEO_OBJECT, базовые линии, ЦД | аудит-хэш-цепочка (verify),Maker–Checker |
| Контур ENG6-PLAN | задачи и результаты — TTL 1 ч / LRU 256 (не персистентны by design; долговременное хранение — у заказчика, FR-INT-01) | NDJSON: sha256 входа без координат, X-Requestor, worker, статус |
| Мост (unified/bridge) | не хранит данных; чистые функции + клиент | протоколы XVER/E2E в unified/protocols/ |

## 5. Открытые архитектурные вопросы (фаза 1)

1. Персистентная очередь линии B: TaskStore → PostgreSQL (интерфейс ADR-006 готов) —
   снимает TTL-ограничение и даёт платформе доступ к истории задач.
2. Prometheus-метрики платформы: /metrics в afina/server (сейчас healthz как up-индикатор).
3. UI-мост: postMessage-контракт «сцена платформы ⇄ планировщик» (состав пакета =
   build_plan_request/plan_to_platform_tables — уже стабилизирован тестами).
4. Расширение XVER на бюджет линии и SINR (Python RF-04/RF-07 ⇄ ENG6.calcLink full):
   потребуется стенд с рельефом (пока terrain.source=flat — расхождение 0.0000 дБ
   подтверждено selfcheck линии B).
