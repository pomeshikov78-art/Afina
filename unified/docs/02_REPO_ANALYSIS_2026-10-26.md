# Комплексный разбор репозитория «Afina»

**Дата разбора:** 26.10.2026 · **Стенд проверки:** песочница Linux x64, 2 vCPU / 1 ГБ, Node v20.20.2, Python 3.11, git 2.39
**Объект:** https://github.com/pomeshikov78-art/Afina (291 файл, ~40 МБ содержимого без node_modules)

---

## 1. Резюме

Репозиторий — **не один продукт, а два независимых потока разработки**, выросших из одной затеи (экспорт чата «ТЗ на систему связи Афина» приложен как свидетель происхождения):

| | **Линия A — СПО «Афина NextGen»** (`afina/`) | **Линия B — ENG6-PLAN** (`eng6-service/` + корневые артефакты) |
|---|---|---|
| Основание | ТЗ.АФИНА.11.0 (ГОСТ 34.602-2020), 83 требования | Дополнение №2 к ТЗ от 16.10.2026 (5 этапов), изделие «Планировщик связи» E6/8.0 |
| Стек | Python 3.11, **stdlib-only, 0 зависимостей** | Node.js ≥ 20.11, **dependencies: {}**, вендор ENG6 в изолированном V8-контексте |
| Код | ~9,8 тыс. строк (ядро пакета `afina` — 5,8 тыс.) | ~14,7 тыс. строк своего JS + вендор ENG6 v5.1.0 (677 тыс. знаков, 151 модель MLIB) |
| Роль | Платформа: ГИС, каталог 1940–2036, ОШС, цифровые двойники, RBAC, аудит-хэш-цепочка, ИИ-RAG, ВТ-профиль, геймификация, веб-клиент с WebGL | Вычислительное ядро: MILP-планирование (ресурсы/маршруты/расписание), REST-микросервис, картографический планировщик, ERP-коннектор, нагруженный стенд, Docker/K8s |
| Тесты (проверено мной) | **145/145** за 6,2 с | **125/125** за 13,8 с; conformance 16/16; selfcheck 21/21 |
| Период | 17–18.10.2026 (рубежи G0–G5) | 16–26.10.2026 (этапы 1–5) |

**Общая оценка:** обе линии individually зеленые и документированы на редкость честно, но между ними **нет ни общей истории git, ни общей математики, ни общего CI**. Сегодня это «комплект для совмещения», а не продукт. Главный нерешённый вопрос — **два источника истины по радиомоделям** (Python ENG6+: 10 моделей; JS ENG6: 151 модель) и **юридический статус извлечённого ядра ENG6**. План совмещения — в разделе 6, развитие — в разделе 7.

## 2. Происхождение: одна затея — две реализации

Хронология по артефактам самого репозитория:

1. **`chat-export-1792180055034.json`** (75 сообщений, 34 пользовательских) — переписка «ТЗ на систему связи Афина»: задача *「описать полностью и подробно два файла в единое ТЗ на СПО планирования и моделирования системы связи "Афина" + цифровые двойники」*. Далее 33 итерации уточнений: русские названия модулей, два режима эксплуатации (автономный контур / Air-Gap), военный профиль, геймификация, реестр требований, приёмка по доказательствам. Финал — «Сделай финальное ТЗ». Важная деталь из сообщения №4: **исходный код 22 перечисленных программ-аналогов закрыт (проприетарен)** — это источник юридической напряжённости (раздел 8).
2. **Линия A (17–18.10):** по итоговому ТЗ.АФИНА.11.0 построена эталонная реализация G0–G5: 13 коммитов в git-бандле, все — **за один день 18.10.2026 с 12:22 до 14:40** (первый коммит — «Восстановление истории: состояние после G2», т.е. ранняя история g0/g1/g2 утеряна и заменена снимком). Параллельно — демо-трек: 7 концептов-прототипов → однофайловые версии `Афина_v1…v12.html`.
3. **Линия B (16–26.10):** из изделия `comms_planner_v8.0_headless.html` (2 551 730 байт, 5 скриптовых блоков: ENG6 — 677 168 знаков, APPCORE6 — 146 821, SHELL6 — 239 026, R52·S0 — 909 858) **побайтово извлечено ядро ENG6 v5.1.0** (69 ключей фасада, sha256 `adb610c9…`), и поверх него построен промышленный сервис ENG6-PLAN: ядро → API → UI → нагрузочный стенд → инфраструктура. Результаты нагрузки датированы 20.10, публикация в GitHub — 26.10 тремя коммитами «Add files via upload».

Связь линий сегодня — только общая предметная область и слово «Афина». В `Афина_v12.html` ядра ENG6 нет (0 вхождений MLIB); в `comms_planner_v8.0_headless.html` нет платформы «Афины».

## 5. Оценка состояния работы

### 5.1. Сильные стороны (редкие для проектов такого темпа)

1. **Культура честности как инженерная практика.** RTM «35/83 подтверждено автоматизированно» — без накрутки; 48 требований честно помечены «стенд/данные/вручную по ПМИ». Прогнозная техника до 2036 маркирована «ПРОГНОЗ — не подтверждено». Сценарные результаты ЦД — всегда «оценка (не факт)». Суррогатная модель маркируется «СУРРОГАТ», за пределами домена — честный отказ. Акт приёмки — «проект, подпись комиссии Система не подменяет».
2. **Приёмка по доказательствам, а не по демонстрации** (ТЗ §15): 11 семейств протоколов, генератор акта заново прогоняет тесты при каждом запуске; в линии B — selfcheck 21 проверка, конформанс 33+5 блокирует сборку Docker-образа.
3. **Изоляция и автономность действительно проверены:** AUT-T02 — 44 теста при заблокированном сокете, 0 исходящих; V8-tripwire на браузерные API в вендоре ENG6; статическое сканирование импортов ядра; CSP/no-store/fail-fast TLS; обе линии zero-dependency — идеально для Air-Gap (режим Б).
4. **Реестр дефектов линии B (16 шт.)** — образцовый: причина → последствие → способ устранения → регрессионный тест. Плюс 5 задокументированных отклонений от ТЗ с обоснованием и 8 ADR.
5. **Детерминированность** как требование обеих линий (побайтово одинаковый выход; проверяется тестами).
6. **Масштаб линии B подтверждён нагрузкой:** 4 рубежа backpressure, шквал 40×2000 узлов без падений и перезапусков воркеров, адаптивный лимит кучи, graceful shutdown.
7. **Документационный комплект ГОСТ 34.602** практически полный в обеих линиях (ТЗ + Дополнения, ПМИ, руководства, регламенты, SBOM, модель угроз, реестр лицензий/рисков).
8. **UX-трек** (7 концептов → 12 версий → акт эталона) — готовый материал для согласования интерфейса с заказчиком; демо-инструкция с «честными ответами на вопросы» и списком «чего нельзя обещать».

### 5.2. Проблемы, разрывы и риски

**Критические (блокируют совмещение/промышленную эксплуатацию):**

Ирония: требование **ARC-002 (P0)** «Абстракция вычислительного бэкенда: один расчёт воспроизведён на двух типах вычислительного пути в пределах допуска» — как раз не подтверждено. ### 6.3. Чего делать НЕ следует

1. **Не переписывать JS-ядро (677 КБ, 151 модель) на Python.** Это ровно то, от чего линия B осознанно отказалась (ADR-001, отклонение №1: «два источника истины, конформанс 33+5 пришлось бы восстанавливать заново»). Обратная операция — та же ловушка.
2. **Не выбрасывать Python ENG6+.** После шага 6 он становится независимым верификатором (закрывает P0-требование ARC-002 «два вычислительных пути») и резервным ядром для режима Б на машинах без Node.
3. **Не сливать два UI в один файл «сразу».** Сначала фрейм+мост (дешевле, сохраняет FPS и тесты обеих сторон), потом постепенный перенос.
4. **Не включать вендор ENG6 в открытую поставку до решения К2.** Публичный GitHub-репозиторий с извлечённым проприетарным ядром — уже риск; как минимум нужно ограничить видимость репо до завершения IP-аудита.

## 7. Дорожная карта развития на базе «Афины»

**Фаза 0 — гигиена (1–2 недели):** шаги 1–4 раздела 6.2 (IP-аудит запустить параллельно). Результат: монорепо, CI зелёный, 0 известных дефектов смоуков.

**Фаза 1 — совмещение (1–2 месяца):** шаги 5–10. Результат: единый продукт «Афина» с каноническим расчётным ядром ENG6-JS; **ARC-002 закрыт протоколом кросс-верификации**; RTM ~150 требований с честным покрытием; демонстрация сквозного сценария «каталог → сцена → план развертывания → расписание → выгрузка в ERP».

**Фаза 2 — продуктовая крепость (3–6 месяцев):**
- PostgreSQL/PostGIS в проде (схема готова, AUT-001 «единое ядро» соблюдается) + персистентная очередь ENG6-PLAN (TaskStore → PG/Redis, интерфейс по ADR-006 готов) — снимает TTL-ограничение результатов;
- данные рельефа заказчика (MTW/DB3D) + тайловый конвейер (готов) + SXF/SITX-адаптеры после лицензирования форматов;
- локальная LLM (GGUF-раннер как опция ИИ-слоя; детерминированный RAG остаётся базой — AUT-002 запрещает внешние API);
- порт тяжёлых участков: Rust/N-API-аддон для графового подслоя (прямо предложен в ADR-002) либо C++/Vulkan-порт ядра с обязательной регрессией по эталонам MOD-002/004 (позиция 2 ограничений);
- сборка и подписание .exe на Windows-стенде (AUT-T04), обкатка на Astra Linux / Эльбрус;
- полный 3D SBR/ray-tracing и UTD после GPU-порта (позиция 9 ограничений).

**Фаза 3 — приёмка и сертификация (6–12 месяцев):** СКЗИ по классу системы (интерфейс CryptoProvider готов), нагрузочные S3/S4 на целевом железе, аппаратурная часть MIL-05/10, закрытие оставшихся 48 позиций RTM по ПМИ, приёмка комиссией заказчика (§15 — проект акта уже сгенерирован).

**Продуктовые направления (маркетинговые ходы на готовом заделе):**
1. **«Планирование развертывания как сервис цифрового двойника»**: DT-5 сценарии (trend/param/degradation) + ENG6-PLAN + перекрёстная проверка = уникальная связка «спланировал → оценил деградацию → перепланировал» с паспортацией каждого запуска.
2. **Учебный центр**: геймификация §4.11 (9 миссий, полигон 8 этапов, компетенции 0–5), учебные миссии v11 («Найди ошибку в паспорте») — готовый продукт для вузов/учебных центров войск связи.
3. **Реестр моделей с V&V-паспортами** как точка расширения: подключение моделей заказчика через суррогаты MOD-006 (честный out_of_domain, валидация только ролью verify) — платформенная монетизация.
4. **ERP/OSS-коннектор** (Путь А) — отдельная малая поставка для интеграции с учётными системами без полного развёртывания платформы.

## 9. Заключение

Проделана большая и качественно задокументированная работа: две независимые эталонные реализации (платформа «Афина NextGen» на Python и вычислительный сервис ENG6-PLAN на Node) суммарно ~24,5 тыс. строк собственного кода, 270 автоматических тестов (145+125), 11 семейств протоколов, полные комплекты документации ГОСТ 34.602 — и всё это **воспроизводится с первого запуска** (проверено).
