# 01_OBSERVATIONS — наблюдения интеграционных прогонов единой программы

Журнал честных наблюдений при совместных прогонах обеих линий (аналог реестра
дефектов линии B `eng6-service/docs/06_DEFECTS.md`, но для интеграционного слоя).
Политика: наблюдаем → измеряем → документируем → правим только свою зону
(артефакты линии A/B не изменяются без решения их владельца).

## OBS-02 · Единицы fresnelR вендора ENG6 (XVER-FRESNEL)

`ENG6.PROP.fresnelR(d1,d2,f)` возвращает значение в √1000 ≈ 31,6228 раза больше
эталона RF-06 (`17.32·√(n·d1·d2/(f·d))`, м) — смешение м/км в формуле вендора
(проверено по исходнику функции: `sqrt((300/f)·(d1·10³)·(d2·10³)/(d·10³))`).
Вендор неизменяем (§9.3.1 Доп. №2) → согласование `b_scale_div=√1000`
в `backend_arc002.ALIGNMENTS`, после него Δ ≤ 0.001 м на всей сетке.
**Рекомендация**: в UI/отчётах линии B не использовать `fresnelR` напрямую без
нормировки; на стороне платформы RF-06 остаётся эталоном.

## OBS-03 · Семантика `hata(suburban)` вендора ENG6 (XVER-HATA-SUBURBAN)

`ENG6.PROP.hata(f,d,h1,h2,'suburban')` ≡ `'urban'` (поправка пригорода не
применяется); Python ENG6+ применяет стандартную поправку −2·lg²(f/28)−5.4 дБ
(до 9.94 дБ на 450 МГц). Вендор неизменяем → точки suburban исключены из стадии
ALIGNED с обоснованием; при планировании через ENG6-JS для пригорода применять
`env='urban'` (консервативно: потери выше) либо поправку на стороне платформы.

## OBS-04 · CM-поправка COST-231 (XVER-COST231-CM)

`ENG6.PROP.cost231(f,d,h1,h2,env)` при любом переданном env добавляет CM=+3 дБ
(без env — не добавляет). Python `cost231_hata_db(..., cm_db=0)` по умолчанию.
Согласование: платформенная сторона передаёт `cm_db=3.0` — Δ=0.0 дБ на всей сетке.
Учтено в `ALIGNMENTS`; в реестре моделей платформы внести примечание для пары.

## OBS-05 · Дубли нумерации И-* в Дополнении №2

В исходном документе два разных требования обозначены «И-05» (визуальный
контроль §7.1 и Docker §7.2), порядок И-04/И-05 переставлен. При транскрипции
в единый RTM введены префиксы `И-НГ-*` (нагрузочные) и `И-ИНФ-*`
(инфраструктурные) с сохранением `source_id`. Рекомендуется исправление
нумерации в следующей редакции Дополнения №2.

## OBS-06 · Порог отсечки дифракции J(v): −0.7 (Python) против −0.78 (вендор)

Формулы ITU-R P.526 идентичны (6.9+20·lg(√((v−0.1)²+1)+v−0.1)) и совпадают
побайтово на всей сетке XVER (Δ=0.0 дБ, 16 точек). Расходятся только пороги
нулевой отсечки: `rf.py::_diffraction_epsilon` — v ≤ −0.7 → 0 дБ;
`ENG6.PROP.knifeEdgeJ` — v ≤ −0.78 → 0 дБ. Измерено в полосе (−0.78; −0.7]:

| v | ENG6, дБ | Python, дБ | Δ, дБ |
|---:|---:|---:|---:|
| −0.75 | 0.2011 | 0 | 0.2011 |
| −0.71 | 0.4685 | 0 | 0.4685 |
| −0.70 | 0.5361 | 0 | 0.5361 |

Максимальное расхождение 0.54 дБ — мало для решений по запасу (типичный
minMarginDb = 3), но зафиксировано честно: сетка XVER полосу минует,
примечание — в `PAIRED_MODELS["DIFFRACTION_J"].note` и в протоколе.

## OBS-07 · RBAC платформы: «Администратор системы» не может создавать объекты

Интеграционный тест сначала падал с HTTP 403: операция `edit_models_cond`
недоступна роли «Администратор системы» (SEC-001, матрица Прил. Н). Это НЕ
дефект, а штатное наименьшее полномочие: единая программа работает под двумя
ролями — администратор (аудит/регистрация) и «Инженер-расчётчик» (обстановка).
Зафиксировано в test_platform_bridge (403-проверки в обе стороны — теперь
регрессионный барьер на состав ролей).

## OBS-08 · Контракт attrs платформы — JSON-объект, не строка

`POST /api/v1/objects` сериализует `attrs` сам (`json.dumps(body.attrs)`);
передача уже сериализованной строки даёт двойное кодирование. Клиент моста
(`scenario_export`) передаёт dict; `_attrs()` defensively разворачивает двойное
кодирование для legacy-строк. Рекомендуется внести в API-спецификацию линии A.

## OBS-09 · GitHub отклоняет запись .github/workflows/ токеном без scope «workflow»

При синхронизации прохода №2 push был отклонён: «refusing to allow a Personal
Access Token to create or update workflow .github/workflows/unified-ci.yml
without `workflow` scope». Это штатная защита GitHub, не дефект репозитория.
Решение (выбрано): workflow-файл исключён из git-истории (источник истины —
`unified/ci/unified-ci.yml`), локальная копия `.github/` — вне индекса
(.gitignore). Активация CI: создать `.github/workflows/unified-ci.yml` через
веб-интерфейс GitHub (скопировав содержимое источника) либо выполнить push
токеном со scope `workflow`. Урок процесса: fine-grained PAT для синхронизации
выдавать с правами Contents:RW **и** Workflows:RW, либо не включать workflow-
файлы в автоматические push.

## OBS-10 · REL/NET-пары не создаются осознанно; NET-01 ⇄ FIBER — согласование параметризации

1. **REL-01 (SPOF) ⇄ ENG6.NET.criticalNodes — НЕ парируется (решение).**
   Семантики различаются по существу: Python `find_spof` — сервисно-ориентирован
   (удаление узла разрывает пару «источник услуги — потребитель»), ENG6
   `criticalNodes` — связностно-ориентирован (lostPct/breaksNet при удалении).
   Формальное сопоставление дало бы ложные «расхождения» на концевых узлах.
   Графовый подслой линии B УЖЕ сверен с ENG6.NET (23 теста graph.test.mjs:
   компоненты, мосты, точки сочленения) — дублировать сверку через Python
   неценесообразно. Статус: задокументированное решение, не пробел.

2. **NET-01 (оптический бюджет) ⇄ ENG6.FIBER.loss — пара XVER-FIBER-PARAMS.**
   Формулы идентичны (км·att + сростки·splice + коннекторы·conn), но параметризация
   разная: ENG6 фиксирует 2 коннектора и сростки каждые 4 км; Python NET-01 принимает
   явные количества (дефолт 4×0.5 дБ + 2×0.1 дБ). RAW-стадия честно показывает разницу
   дефолтных комплектов (до 1.3 дБ на 100 км); ALIGNED — параметризация ENG6
   (connectors=2, splices=⌊км/4⌋), после чего Δ ≤ 0.011 дБ (округление бюджета
   Python до 2 знаков). Вывод для платформы: при сопоставлении с планом ENG6-PLAN
   использовать в OpticalLink явные количества из пресета линии (LINK_PRESETS.FOC.fiber:
   att 0.22, splice 0.05, conn 0.3).

## OBS-11 · RF-07 не моделирует поглощение в атмосферных газах (зазор относительно ENG6)

Композитные пары XVER уровня `ENG6.calcLink` (CALC_LINK_PROP/RX/NOISE) построены
на частотах ≤ 900 МГц, где `gasGamma(f, 15°C, 60%) = 0.000000 дБ/км` — на этих
частотах бюджет Python RF-07 и calcLink совпадают до округления (Δ ≤ 0.005 дБм).

Измерено (зонд, 15 °C / 60 %):

| f, МГц | gasGamma, дБ/км | На 50 км, дБ |
|---:|---:|---:|
| 900 | 0.000000 | 0.00 |
| 1400 | 0.001838 | 0.09 |
| 1500 | 0.001965 | 0.10 |
| 2000 | 0.002603 | 0.13 |
| 7000 | 0.010891 | 0.54 |

Python `LinkBudget` (RF-07) члена поглощения в газах НЕ имеет. На РРЛ-диапазонах
(7–8 ГГц) и длинных пролётах это даёт систематическую оптимистичность бюджета
платформы до ~0.5 дБ и более. Это НЕ подгонка допуска, а граница применимости
пары: точки f ≥ 1400 МГц в композитную сетку не включены и будут добавлены после
устранения зазора.

**Рекомендация линии A**: добавить в `LinkBudget` поле `gas_absorption_db`
(внешний член, как `diffraction_db`) либо брать член из breakdown.prop модели
ENG6 при совместных расчётах; до этого в паспорте RF-07 для f > 1 ГГц фиксировать
допущение «поглощение в газах не учтено (оптимистично, ≤ 0.011 дБ/км)».
